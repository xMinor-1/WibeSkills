# TRIZ Toolkit — рабочий справочник (читать в рантайме)

Свод инструментов ТРИЗ Альтшуллера, переведённый на язык продуктовых/бизнес-задач.
Скилл `triz-resolve` читает этот файл, чтобы опираться на канон, а не на память модели.
Инженерные примеры заменены продуктовыми, но логика приёмов сохранена дословно.

---

## 1. Идеальность и ИКР

**Закон идеальности:** система развивается в сторону роста идеальности = (сумма полезных функций) / (сумма затрат и вреда). Идеальная система — функции есть, системы нет.

**ИКР (Идеальный конечный результат)** — формулируется ДО решения, как планка:
> «Элемент САМ выполняет функцию X, без [ресурса/шага/усилия Y], не создавая [вреда Z], в нужный момент.»

Правила ИКР:
- Не «как сделать машину дешевле», а «функция выполняется, машины нет».
- «Сам» — ключевое слово: ресурс должен появиться из системы, а не извне.
- ИКР недостижим буквально — он показывает направление и меру слабости текущего решения.

## 2. Противоречия — три уровня

1. **Административное** — «плохо, надо улучшить, не знаю как». Не решается, только переформулируется вниз.
2. **Техническое (ТП)** — «улучшаю параметр А → ухудшается параметр Б». Пара конфликтующих характеристик.
3. **Физическое (ФП)** — «один и тот же параметр должен быть И таким, И противоположным». Самый глубокий уровень; отсюда сильные решения.

Правило: дожимай административное → техническое → физическое. Формулировка ФП:
> «[Параметр] должен быть [большим], чтобы [функция1], и [малым], чтобы [функция2].»

---

## 3. Разрешение физического противоречия — 4 разделения (ядро метода)

- **Во времени** — противоположные состояния в разные моменты. (Строгая верификация при первой сделке — ноль трения в повторных.)
- **В пространстве / структуре** — в разных частях системы. (Жёсткий флоу для новичков, экспресс-ветка для доверенных.)
- **В надсистеме / подсистеме (по уровням)** — конфликт снимается уровнем выше или ниже. (Проверяем не мы, а сеть/скоринг/партнёр/сам пользователь.)
- **По условию** — состояние зависит от условия. (Бесплатно для сегмента роста, платно для сегмента маржи.)

Порядок применения: сначала пробуй **разделение во времени** (чаще всего срабатывает), затем в пространстве, затем по уровням, затем по условию.

## 4. 40 приёмов Альтшуллера → продуктовый перевод

| # | Приём | Продуктовый смысл |
|---|---|---|
| 1 | Дробление | распилить фичу/тариф/процесс на независимые модули |
| 2 | Вынесение | вынести мешающую/нужную часть отдельно (тяжёлый шаг — в фон, ключевую функцию — в отдельный продукт) |
| 3 | Местное качество | разные части системы — разные свойства (разный UX на сегмент) |
| 4 | Асимметрия | сломать симметрию (не единый флоу, а скошенный под кейс) |
| 5 | Объединение | слить однородные операции/экраны в один проход |
| 6 | Универсальность | один элемент делает несколько функций (одно поле = поиск+фильтр+создание) |
| 7 | Матрёшка | вложенность, прогрессивное раскрытие (one screen с уровнями) |
| 8 | Антивес | компенсировать минус внешней силой/партнёром (субсидия, реферал) |
| 9 | Предварительное антидействие | заранее нейтрализовать будущий вред (guardrails до запуска) |
| 10 | Предварительное действие | сделать работу заранее (предзаполнение, прогрев, прекомпьют) |
| 11 | «Заранее подложить подушку» | заранее подстраховать риск (fallback, ретраи, страховка сделки) |
| 12 | Эквипотенциальность | убрать лишние «подъёмы» — не заставлять юзера менять уровень (без лишних переходов/логинов) |
| 13 | Наоборот (инверсия) | перевернуть: не юзер к нам, а мы к юзеру; не искать груз — груз находит тебя; сделать неподвижное подвижным |
| 14 | Сфероидальность | заменить прямые/резкие ходы плавными (мягкий онбординг вместо стены форм) |
| 15 | Динамичность | сделать жёсткое адаптивным (персонализация, авто-подстройка параметров) |
| 16 | Частичное/избыточное действие | если «точно» трудно — сделать чуть меньше или чуть больше и добрать (черновик→доводка) |
| 17 | Переход в другое измерение | вынести в 2D/многослойность, использовать обратную сторону (второй экран, фон, доп. канал) |
| 18 | Резонанс | попасть в собственную частоту системы (тайминг под ритм пользователя/рынка) |
| 19 | Периодическое действие | вместо непрерывного — импульсами (дайджест вместо потока нотификаций) |
| 20 | Непрерывность полезного действия | убрать простои, элемент работает всегда (фон-процессы, всегда-актуальные данные) |
| 21 | Проскок | вредный этап пройти быстро (пропустить/автоматизировать болезненный шаг) |
| 22 | Обратить вред в пользу | вредный фактор → ресурс (ошибка → сигнал, отказ → лид, простой → апселл) |
| 23 | Обратная связь | ввести/усилить/инвертировать feedback loop (сигнал системе о результате) |
| 24 | Посредник | промежуточное звено-агрегатор/брокер, снимаемое после |
| 25 | Самообслуживание | система обслуживает и чинит себя сама (автоставки, автоматизация, self-serve) |
| 26 | Копирование | заменить дорогой объект дешёвой копией/симуляцией (шаблон, макет, digital twin) |
| 27 | Дешёвая недолговечность | одноразовое дешёвое вместо дорогого долговечного (disposable-флоу, временные окружения) |

| 29 | Пневмо/гидро-конструкция | заменить жёсткое гибким/текучим (гибкая конфигурация вместо хардкода) |

| 33 | Однородность | взаимодействующие объекты — из одного «материала» (единый формат данных, один язык интеграции) |
| 34 | Отброс и регенерация | отработавшее удалять, недостающее восстанавливать (авто-clean-up, регенерация квоты) |

| 36 | Фазовый переход | использовать скачок состояния (триггерный порог, смена тарифа при событии) |
| 37 | Тепловое расширение | использовать реакцию на «нагрев»/нагрузку (авто-масштабирование под спрос) |
| 38 | Сильный окислитель / усиление среды | усилить активную среду (более концентрированный сигнал/оффер в момент пика) |
| 39 | Инертная среда | наоборот, обезопасить средой (песочница, дефолты-без-вреда) |
| 40 | Композиты | смесь разнородного вместо однородного (гибридная модель: правила + ML + человек) |

Использовать как чек-лист: прогнать конфликт по приёмам, отобрать 2–4 применимых, а не перебирать все 40 вслух.

## 5. Вещественно-полевые ресурсы (ВПР)

Сильное решение использует ресурс, за который уже заплачено. Инвентаризация:
- **Ресурсы системы** — данные, которые уже копятся; действия, которые юзер и так делает; вычислительные мощности в простое.
- **Ресурсы надсистемы** — трафик соседнего продукта, экосистема, партнёры, отраслевые реестры.
- **Ресурсы среды** — сезонность, поведение конкурентов, регуляторика, «бесплатные» внешние сигналы.
- **Вредные ресурсы** — то, что мешает: обратить в пользу (приём 22).
- **Производные ресурсы** — то, что можно получить преобразованием имеющегося почти даром.

Правило: прежде чем строить новое — спроси «какой ресурс уже есть в системе и простаивает».

## 6. Законы развития систем (диагностика зрелости продукта)

1. **Полнота частей** — жизнеспособная система = двигатель + трансмиссия + рабочий орган + управление. Чего не хватает в продукте?
2. **Энергопроводимость** — сквозной проход ценности/данных без разрывов. Где рвётся поток?
3. **Согласование ритмов** — частоты частей согласованы (тайминги, циклы релизов/уведомлений).
4. **Рост идеальности** — функций больше, системы/затрат меньше.
5. **Неравномерность развития частей** — узкое место тормозит всё; конфликты возникают на отстающей части.
6. **Переход в надсистему** — исчерпав себя, система становится частью большей (продукт → платформа → экосистема).
7. **Микроуровень / поля** — переход от «механики» к более управляемым «полям» (ручное → данные → алгоритмы).
8. **Динамизация** — рост гибкости и управляемости (статичное → адаптивное → само-настраиваемое).

---

## 7. АРИЗ — сжатый алгоритм (каркас для сложной задачи)

1. Сформулировать мини-задачу: «всё как есть, но вредного действия/затрат нет».
2. Выделить конфликтующую пару и техническое противоречие.
3. Довести до физического противоположения к одному элементу (оперативная зона + оперативное время).
4. Записать ИКР: X-ресурс сам устраняет конфликт, ничего не усложняя.
5. Найти ресурс в оперативной зоне/времени (ВПР).
6. Разрешить ФП разделением (§3) + приёмами (§4).
7. Проверить решение на идеальность и на новые противоречия; сильное — снимает конфликт, не балансирует.

---

## 8. Критерий силы решения (финальный фильтр)

Решение сильное, если:
- убрали элемент/шаг — а функция осталась;
- использован внутренний, уже оплаченный ресурс;
- физическое противоречие **разрешено** (разделено), а не разменяно компромиссом;
- не породило нового, худшего противоречия.

Если итог звучит как «нашли баланс / золотую середину» — решение слабое. Вернуться к §2 и дожать противоречие.
