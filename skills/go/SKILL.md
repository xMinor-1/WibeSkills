# go — перенос работы в фоновую сессию, переживающую обрыв связи

## Что это делает

Запускает **отдельный Claude Code внутри tmux** на сервере:

- tmux не привязан к SSH/VS Code → обрыв связи, закрытый ноут и упавший extension host его не убивают;
- фоновая сессия форкает контекст текущего чата (`--resume <id> --fork-session`) — помнит всё, о чём говорили;
- работает headless (`--print`): отрабатывает задачу до конца и выходит, никаких вопросов и подтверждений;
- **итог возвращается в чат сам**: вахта `await` будит этот чат по завершении рана;
- **дополнения на лету**: `go.sh say` кладёт сообщение в очередь живого рана — он подхватит
  его после текущего прохода и продолжит в фоне;
- **авто-восстановление**: cron-watchdog каждые 2 мин перезапускает упавший ран продолжением
  той же сессии (до 3 рестартов); переживает и перезагрузку сервера;
- текущий чат остаётся живым и свободным.

Движок — `go.sh` в папке скилла. Раны лежат в `~/.claude/go-runs/<name>/`
(`task.txt`, `prompt.txt`, `meta.env`, `state`, `inbox/`, `raw.log`; `REPORT.md` пишет сама
сессия — требование скрипт дописывает в каждый промпт автоматически). Повтор имени
завершённого рана не удаляет его папку, а убирает в `~/.claude/go-runs/.old/`.

## Как выполнять

### 1. Собери ТЗ для фоновой сессии

Фоновая сессия **не может задать вопрос** — некому ответить. Промпт должен быть
самодостаточным ТЗ, даже при наследовании контекста:

- что именно сделать — конкретно, по пунктам;
- где — пути, проект, прод/локально;
- критерий готовности — «страница открывается и отдаёт 200», «тесты зелёные»;
- поведение на развилке: выбрать разумный вариант, продолжить, зафиксировать выбор в отчёте —
  **не останавливаться и не ждать**;
- запреты: не пушить в прод / не трогать чужие файлы / удалять только в `archive/_trash-YYYY-MM-DD/`;
- финал: базовое требование «запиши итог в REPORT.md» скрипт добавит сам; если отчёт нужен
  в особом разрезе (что проверить владельцу, какие метрики снять) — пропиши это в ТЗ явно.

Если пользователь написал просто `/go` без задачи — сформулируй ТЗ сам из того, над чем работаем
сейчас, и покажи его одной строкой в ответе.

### 2. Запусти

```bash
"<папка скилла>/go.sh" run "<ТЗ одним текстом>" --name <короткое-имя> --dir "<корень проекта>"
```

- контекст текущего чата наследуется автоматически (из env `CLAUDE_CODE_SESSION_ID`);
  `--fresh` — чистая сессия, если контекст не нужен (дешевле);
- права по умолчанию `bypassPermissions` — иначе фон встанет на первом же вопросе;
  `--safe` (acceptEdits) — если задача трогает чужой прод;
- `--dir` указывай явно: корень проекта, а не cwd bash-инструмента;
- `--effort` наследуется из текущей сессии (env `CLAUDE_EFFORT`); `--model` НЕ наследуется —
  без флага фон стартует на модели из глобальных настроек. Если чат работает на другой модели
  и это важно — укажи `--model` явно.

### 3. Поставь вахту завершения (обязательно, сразу после запуска)

Вызови Bash с `run_in_background: true`:

```bash
"<папка скилла>/go.sh" await <имя>
```

Команда тихо ждёт и завершается, когда ран доходит до терминального состояния
(`finished` / `failed` / `stopped`) — в чат придёт уведомление о завершении фоновой
команды. По этому уведомлению, **не дожидаясь вопроса пользователя**:

1. верни результат по правилам `/goon` (`REPORT.md` + `go.sh log`, проверить ключевые
   утверждения, доложить; упавший ран подавать как упавший);
2. отметь доклад: `go.sh ack <имя>` — иначе хук-напоминалка будет поднимать это снова;
3. если ран работал дольше ~5 минут (пользователь мог отойти) — отправь `PushNotification`
   одной строкой с сутью итога.

### 4. Доложи пользователю коротко

- имя рана и что ему поручено — одна строка;
- скажи: результат вернётся в чат сам, когда ран закончит; раньше срока — `/goon`;
- дополнения к задаче можно писать прямо в чат — ты перешлёшь их в фон (см. шаг 5).

### 5. Пока ран жив — дополнения уходят в фон, чат остаётся свободным

Если пользователь дописывает что-то **по задаче рана** («и ещё …», «не забудь …», «поменяй …»):

```bash
"<папка скилла>/go.sh" say <имя> "<дополнение одним самодостаточным текстом>"
```

- живой ран подхватит дополнение **после текущего прохода** (не мгновенно — скажи это одной строкой);
- завершённому рану `say` сам запустит продолжение той же сессии (аналог `more`) —
  в этом случае заново поставь вахту `await` (шаг 3);
- формулируй дополнение самодостаточно: фон не видит этот чат после форка;
- сообщения **не по задаче рана** — делай в чате как обычно, в фон не пересылай;
- непонятно, туда ли — переспроси одной строкой.

## Управление ранами

```bash
go.sh list                 # какие раны есть и что с ними
go.sh status <name>        # состояние, очередь inbox, счётчик рестартов
go.sh log <name> [N]       # последние N сообщений (чистый текст из jsonl сессии)
go.sh tail <name>          # живой хвост вывода терминала
go.sh say <name> "<текст>" # дополнение: живому — в очередь, завершённому — новый заход
go.sh more <name> "<...>"  # продолжить ЗАВЕРШЁННУЮ сессию новой задачей
go.sh await <name>         # вахта завершения (запускать в run_in_background)
go.sh ack <name>           # отметить «итог доложен» (гасит напоминания хука)
go.sh back <name>          # id рана + готовые команды для ручного возврата
go.sh stop <name>          # остановить; watchdog остановленное НЕ воскрешает
go.sh attach <name>        # подключиться к окну tmux (только из живого терминала)
```

`attach` из чата не вызывай — он блокирует терминал. Состояние проверяй через `log`/`status`.
Ручной возврат результата в чат — скилл `/goon` (SKILL.md рядом: `../goon/`).

## Авто-восстановление (watchdog)

`go.sh run` идемпотентно ставит cron-задачу: каждые 2 минуты `go.sh watchdog` ищет раны
в состоянии `running`, у которых умер tmux (упал процесс, перезагрузился сервер), и
возобновляет их продолжением той же сессии (`--resume`), до 3 рестартов на ран
(счётчик `.restarts`). Плюс сам раннер ретраит упавший `claude` до 2 раз внутри tmux.

- останавливать ран только через `go.sh stop` — он ставит стоп-метку, watchdog его не тронет;
  `tmux kill-session` руками watchdog расценит как падение и воскресит ран;
- после исчерпания рестартов ран помечается `failed`, приписка уходит в REPORT.md;
- интерактивные (`--tui`) раны watchdog не трогает.

## Ограничения (говорить честно)

- Фон работает под тем же аккаунтом → ест тот же 5-часовой лимит, что и этот чат.
  Watchdog с рестартами тоже: упавший ран догоняет задачу за счёт лимита.
- Режим headless: живого диалога с фоновой сессией нет. Дополнения — `go.sh say`
  (подхват после текущего прохода), догрузка завершённого — `go.sh more`.
- Авто-доклад работает, **пока жив этот чат** (вахта await — часть чата). Если чат закрыт —
  при следующем сообщении в этом же чате напомнит хук; из нового чата результат забирается
  скиллом `/goon`. Для ранов с `--fresh` хук не работает (нет родительского чата) —
  там только вахта await или ручной `/goon`.
- `--tui` (интерактивное окно, к которому можно подключиться и переписываться) работает:
  CLI залогинен 02.08.2026. Но `bypassPermissions` в интерактивном окне требует разового
  подтверждения диалога — пока владелец его не принял, скрипт сам понижает права до `acceptEdits`
  и пишет об этом. Не нажимай это подтверждение за владельца.
- MCP-коннекторы с интерактивной OAuth (claude.ai, Notion, Drive) в фоне могут быть недоступны —
  задачи под них в фон не отдавать.
- `bypassPermissions` = никто не спросит подтверждения: разрушительные операции запрещай в ТЗ явно.
