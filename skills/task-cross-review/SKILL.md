# Task Cross Review

Прогоняешь diff через **две модельные линзы + машинные проверки**. Task в статусе `review` в `stories.md`.

**Ревьюер строго выше исполнителя** ([executor-protocol.md](../_shared/executor-protocol.md)). Ревью
одного уровня с тем, кто писал код, — это не ревью: обе стороны слепы к одному и тому же.
`EXECUTOR: inherit` (топ-модель пишет сама) — ревью на той же топ-модели с высоким effort.

Контекст — `../_shared/project-config.md` + проектный `CLAUDE.md`. Approve — `../_shared/approve-protocol.md`. Бэклог — `../_shared/backlog.md`. Хендофф — `../_shared/handoff-protocol.md`. Worktree — `../_shared/worktree-protocol.md`.

## Режим (app-only)

Прочитай `MODE` — `../_shared/mode.md`. Если `MODE: work` — **стоп, не разворачивай pipeline**: в work-режиме финальный код пишет живой программист. Объясни это одной строкой и предложи `dev-handoff` (handoff-пакет) либо `epic-tech-spec` (спека для разработчика). Жди решения. Если `app` или MODE не задан — пропусти этот блок, работай как обычно.

## Workflow-режим (внутри `delivery-run`)

В авто-оркестрации **линзы запускает сам оркестратор** параллельными read-only сабагентами (сабагент не может спавнить вложенных) — промпты берёт из Шага 2 ниже, синтез и вердикт делает по Шагу 3. Сабагент-ревьюер одной линзы: читай diff, верни structured output с находками (file:line, severity), — без хендоффов и записи статусов. Лимит петли 2 раунда считает оркестратор; исчерпан → `needs_decision`. Контракт — `../_shared/delivery-workflow.md`.

**Частота: машинные проверки на каждую Task, модельные линзы — на Story целиком.** Скрипт дёшев
и ловит дефект сразу; линзы на каждой Task из восьми — восьмикратная плата за то, что ревьюер
всё равно увидит связнее одним куском. Исключение — Task с approve-поверхностью (миграции,
auth/payments): её линзы прогоняются сразу, не дожидаясь конца Story.

## Старт

Approve **не нужен**. Иду делать. Worktree Story уже существует на диске — `cd` в него (`git worktree list`).

## Шаг 1: Diff

```bash
git diff <MAIN_BRANCH>...feature/<epic-slug>/<story-slug>
git log <MAIN_BRANCH>..feature/<epic-slug>/<story-slug>
```

## Шаг 2: Что проверяет скрипт, что — модель

Сначала машинные проверки (секунды, не токены). Красная машинная проверка — вердикт уже известен,
модельные линзы не запускай:

| Проверка | Чем | Красная = |
|---|---|---|
| Границы diff по пакету Task | `VERIFY_CMD` / `git diff --name-only` | `BLOCK` |
| Красные тесты не подменены | `git diff` по путям тестов из пакета | `BLOCK` |
| Тесты и типы зелёные | `VERIFY_CMD` | вернуть в build, ревью не тратить |
| Стилистика, мёртвый код, импорты | линтер из `LOCAL_CHECK` | чинится без ревьюера |
| События долетают до `ANALYTICS_PROVIDER` | e2e-фикстура (`task-test` Шаг 3) | `CHANGES REQUESTED` |

Затем **две линзы параллельно** одним сообщением — `Agent` tool, read-only, isolation не нужен.
Модель — из `REVIEWER` (project-config), строго выше исполнителя, effort `high`.

### 1. Безопасность и юр-режим
> «Ревью diff на безопасность: OWASP Top 10 (XSS, инъекции, CSRF, broken auth, sensitive exposure), валидация входов на сервере, требования юр-режима LEGAL_REGIME (персональные данные: шифрование/хеши, не логируем plain; audit-логи на ключевых действиях). Список конкретных уязвимостей с file:line.»

### 2. Соответствие AC и архитектуре
> «Открой `DOCS_ROOT/<epic-slug>/PRD.md` (acceptance criteria, edge cases) и проектный CLAUDE.md (`ARCH_PATTERN`). Сравни реализацию с AC: что покрыто, что не покрыто, где поведение противоречит PRD, все ли edge cases обработаны. Отдельно — нарушения слоёв архитектуры и дублирование существующего кода. Только high-confidence находки с file:line.»

Обе линзы ищут то, чего **нет ни в одном тесте**: расхождение намерения и реализации. То, что
ловится скриптом, им не поручай — это дублирование за деньги.

**Третья линза — только при `EXECUTOR: external:*`** (архитектурное соответствие tech-spec целиком):
чем дешевле и «чужее» исполнитель, тем плотнее ревью.

## Шаг 3: Финальный синтез + разрешение конфликтов

Прочитай `templates/cross-review.md`. Создай `DOCS_ROOT/<epic-slug>/reviews/<task-slug>.md` по структуре.

Линзы независимы — могут давать **противоречивые** рекомендации. Разрешай по приоритету:

1. **Безопасность / юр-режим** — побеждает всегда
2. **Корректность по PRD AC** — следующий
3. **Архитектура и код-стилистика** — последние (часто можно отложить)

В отчёт пиши **разрешённый** список фиксов, не сырые рекомендации каждого.

Сомневаешься в API библиотеки (паттерн кажется устаревшим/новым) — Context7 MCP за свежей докой, чтобы не ловить ложные блокеры.

**Правила вердикта:**
- Любой блокер по безопасности или юр-режиму → `BLOCK`
- **Diff вышел за «Разрешено править» пакета Task** → `BLOCK` (см. ниже)
- Непокрытые AC или незатреканные events → `CHANGES REQUESTED`
- Только minor/nits → `APPROVE`

**Границы пакета (если у Task есть `DOCS_ROOT/<epic-slug>/tasks/<task-slug>.md`).**
До запуска линз сверь `git diff --name-only` со списком «Разрешено править»
(`../_shared/executor-protocol.md`). Любой файл вне списка — `BLOCK`, независимо от качества кода:
расползание правок ломает граф `touches` и параллельность соседних Task. Исключений «зато полезно»
нет — нужная правка вне зоны оформляется отдельной Task. Проверку делает и `VERIFY_CMD`,
но ревью — второй рубеж: `VERIFY_CMD` мог быть не запущен.

Отдельно проверь, что **красные тесты из пакета не изменены**: `git diff <MAIN_BRANCH>...HEAD -- <пути тестов>`
после contract-коммита должен быть пуст. Подогнанный под реализацию тест — `BLOCK`.

## Шаг 4: Обновление бэклога + хендофф

Применяй `../_shared/handoff-protocol.md`.

- **APPROVE** — статус Task в `stories.md` → `testing`, закоммить. Хендофф:
  > Готово: cross-review Task `<task-slug>` — APPROVE, отчёт `DOCS_ROOT/<epic-slug>/reviews/<task-slug>.md`
  > Следующий шаг: task-test
  > Промпт: `Запусти task-test для Task "<task-slug>" эпика "<epic-slug>". Ветка feature/<epic-slug>/<story-slug>, бэклог — DOCS_ROOT/<epic-slug>/stories.md.`

- **CHANGES REQUESTED / BLOCK** — статус Task → `in-progress`, в `stories.md` рядом с Task допиши список фиксов + **счётчик раунда** (`cross-review раунд 1/2`), закоммить. Хендофф назад:
  > Готово: cross-review Task `<task-slug>` — CHANGES (раунд N/2). Что чинить: <список>
  > Следующий шаг: task-build (доработка)
  > Промпт: `Запусти task-build для Task "<task-slug>" эпика "<epic-slug>" — доработка по cross-review (раунд N/2). Список фиксов — в DOCS_ROOT/<epic-slug>/reviews/<task-slug>.md и stories.md. Ветка feature/<epic-slug>/<story-slug>.`

**Лимит петли cross-review ↔ build = 2 раунда per Task.** После 2-го `CHANGES/BLOCK` подряд — не готовь хендофф назад, эскалируй пользователю:
> «Task `<slug>`: после 2 раундов ревью + правок не сходимся. Что не закрылось: <список>. Нужно решение: A) принять как есть, B) переписать с другой стратегией, C) разбить на 2 поменьше.»

## Принципы

- Сначала скрипт, потом модель. Красная машинная проверка — линзы не запускай, вердикт уже есть.
- Обе линзы — **параллельно** одним сообщением; они читают код сами, ты — агрегатор.
- Ревьюер строго выше исполнителя (`REVIEWER` в project-config), effort `high`.
- Confidence-based: minor стилистика без объяснения «почему плохо в нашем контексте» — не в Critical.
- **Считай раунды.** Лимит — 2.
