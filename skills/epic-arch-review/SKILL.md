# Epic Arch Review

Финальный технический gate перед декомпозицией. Здесь — **go / no-go / правки**.

Контекст — `../_shared/project-config.md` + проектный `CLAUDE.md`. Approve — `../_shared/approve-protocol.md`. Хендофф — `../_shared/handoff-protocol.md`. Хранение артефактов — `../_shared/artifact-storage.md`.

## Режим (app-only)

Прочитай `MODE` — `../_shared/mode.md`. Если `MODE: work` — **стоп, не разворачивай pipeline**: арх-ревью — это gate перед моей декомпозицией, а в work-режиме финальный код пишет живой программист. Объясни это одной строкой и предложи `epic-tech-spec` (спека для разработчика). Жди решения. Если `app` или MODE не задан — пропусти этот блок, работай как обычно.

## Старт

Approve **не нужен**. Иду делать.

## Шаг 1: Сбор контекста (параллельно)

1. Читай `DOCS_ROOT/<epic-slug>/PRD.md` и `tech-spec.md`. Нет — стоп.
2. Читай `DOCS_ROOT/*/stories.md` других эпиков в работе — для проверки конфликтов между эпиками (пересечение файлов, схемы БД, паттернов).
3. Запусти subagent `feature-dev:code-architect`: «Оцени, как tech-spec эпика `<X>` ложится на существующую архитектуру `CODE_ROOT`. Конкретно:
   - Clean Architecture (слои, зависимости, направление потока).
   - **SOLID-аудит** по секции «Архитектурные подходы и паттерны» из tech-spec: для каждого принципа — подтверждается ли на коде, или заявление формальное.
   - **Аудит выбранных паттернов**: реальная боль или over-engineering. Особое внимание интерфейсам с 1 реализацией без тестового бенефита, лишним абстракциям на CRUD, паттернам "на будущее".
   - Конфликты с текущими паттернами, точки расширения, технический долг.»
4. Заявлен паттерн / API библиотеки, в актуальности которого не уверен — Context7 MCP за свежей докой (если подключён) перед вердиктом.

## Шаг 2: arch-review.md

Прочитай `templates/arch-review.md`. Создай `DOCS_ROOT/<epic-slug>/arch-review.md` по структуре шаблона.

## Шаг 3: Чек NFR ↔ автопроверка

Пройдись по таблице NFR в PRD. Для каждого NFR проверь, что в tech-spec есть строка с техникой + автопроверкой. NFR без автопроверки — **NO-GO** в `epic-tech-spec` для доуточнения.

## Шаг 3.5: Чек Preview → Code mapping

Для каждого экрана preview (`data-screen`) проверь, что в tech-spec есть строка с компонентом и visual baseline. Mapping пустой / неполный — **NO-GO** в `epic-tech-spec`.

## Шаг 4: Вердикт

- **GO** — всё чисто.
- **GO с правками** — go только после конкретного списка правок.
- **NO-GO** — переписываем PRD или tech-spec; называй конкретно что и почему.

## Шаг 5: Сохранение

Обнови строку `🏗 arch-review.md` в блоке «📚 Артефакты эпика» в `PRD.md` на `✅ <вердикт>`.

## Шаг 6: Хендофф

Применяй `../_shared/handoff-protocol.md`:

- **GO / GO с правками** — следующий шаг `agile-coach decompose`:
  > Готово: arch-review эпика `<slug>` — `DOCS_ROOT/<slug>/arch-review.md`, вердикт: <…>
  > Следующий шаг: agile-coach decompose
  > Промпт: `Запусти agile-coach decompose для эпика "<slug>". PRD, tech-spec, arch-review — в DOCS_ROOT/<slug>/.`
- **NO-GO** — хендофф направлен назад, в `epic-tech-spec` или `epic-prd`:
  > Готово: arch-review — вердикт NO-GO. Что не так: <конкретный список>
  > Следующий шаг: epic-tech-spec (или epic-prd)
  > Промпт: `Запусти epic-tech-spec для эпика "<slug>" — нужны правки по arch-review: <список>. Артефакты — в DOCS_ROOT/<slug>/.`

Юр-ревью (`epic-legal-review`) в pipeline не входит — если эпик трогает ПДн/платежи/рекламу, пользователь запускает его отдельно по своему решению. В хендофф это не вписывай, но если эпик явно юридически нагружен — упомяни одной строкой: «эпик трогает <ПДн/платежи> — стоит прогнать `epic-legal-review` до разработки».

## Принципы

- Не пиши код. Здесь — оценка, не реализация.
- Не угадывай по OWASP — не уверен, пиши «требует ручной проверки».
- Технические требования `LEGAL_REGIME` (хранение/локализация ПДн, логирование), если режим задан, — обязательные пункты ревью. Договорная/юридическая часть — не сюда, это `epic-legal-review`.
- Бэклог других эпиков не читается — стоп, разберись, не давай вердикт без контекста.
- **Бей по over-engineering.** Лишние паттерны и интерфейсы — такой же дефект, как нехватка SOLID. Паттерн «на будущее» без боли → «GO с правками: упростить».
- Секция «Архитектурные подходы и паттерны» в tech-spec пустая или формальная — сразу **NO-GO**.
