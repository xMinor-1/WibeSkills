# Tracker Sync

Ты — мост между **файловым бэклогом проекта** (`DOCS_ROOT/<epic-slug>/stories.md`, формат — `../_shared/backlog.md`) и **внешним трекером**. Ядро pipeline трекер не использует — он живёт на диске. Этот скилл нужен, только если пользователь хочет видеть бэклог в Notion / Linear / Jira: ты выгружаешь и обновляешь, ничего не ломая.

> Скилл сознательно минимальный — допиливается под конкретный трекер по мере надобности. Не входит в auto-pipeline и не готовит хендофф.

Контекст — `../_shared/project-config.md` (раздел «C. Трекер задач») + проектный `CLAUDE.md`. Approve — `../_shared/approve-protocol.md`. Формат бэклога — `../_shared/backlog.md`.

## Конфиг (project-config.md → модуль C)

- `TRACKER` — какой трекер
- `TRACKER_MCP` — имя MCP-сервера или «работаем через UI/CLI»
- `TRACKER_IDS` — ID базы / проекта / доски
- `TRACKER_SCHEMA` — статусы, типы (Epic/Story/Task), поля (Priority/Estimate/Area/Iteration)

Любое поле не заполнено — **стоп, спроси**. Не угадывай ID и не выдумывай схему.

## Старт

Approve **нужен** — запись во внешнюю систему, видимую другим. Короткий план:
> «Синхронизирую <что> с `<TRACKER>`: создам/обновлю N записей. Что меняю в трекере: <…>. Не трогаю: structure / views / schema. ок?»

Без approve — только чтение трекера и diff-отчёт «что разошлось».

## Направление синхронизации

**По умолчанию: файл → трекер.** Источник правды — `stories.md` и артефакты на диске. Трекер — зеркало для удобства просмотра.

Обратное направление (трекер → файл) — только по явной просьбе и с approve: пользователь правил статусы в трекере, хочет подтянуть в файл.

## Режимы

### 📤 Выгрузить эпик (`залей эпик X в трекер`)
1. Прочитай `DOCS_ROOT/<epic-slug>/stories.md` + артефакты эпика (PRD, tech-spec, arch-review и т.д.).
2. Создай / найди страницу эпика (Type=Epic).
3. Под эпиком — Stories (Type=Story), под Stories — Tasks (Type=Task). Иерархия из `stories.md`.
4. Перенеси статусы, parallel groups, deps, AC в поля/Notes по `TRACKER_SCHEMA`.
5. Артефакты эпика — подстраницами или ссылками на файлы в репо (по предпочтению пользователя).

### 🔄 Обновить статусы (`обнови доску` / `синхронизируй статусы`)
1. Прочитай все `DOCS_ROOT/*/stories.md`.
2. Для каждой Story/Task сверь статус с трекером.
3. Покажи diff: что разошлось. После approve — обнови трекер под файл.

### 🔍 Diff-отчёт (`что разошлось с трекером`)
Read-only. Сравни файловый бэклог и трекер, покажи расхождения. Approve не нужен.

## Маппинг статусов

Файловый статус (`backlog.md`) → статус трекера (`TRACKER_SCHEMA`). Типовое соответствие, адаптируй под схему:

| Файл | Трекер (пример) |
|---|---|
| `todo` | To Do / Backlog |
| `in-progress` | In Progress |
| `review` | In Review |
| `testing` | Testing |
| `done` | Done |
| `blocked` | Blocked |

## Паттерны вызовов (логика, не API)

- **Найти задачи эпика:** найти страницу эпика → прочитать детей → для каждого детали.
- **Создать Story под эпик:** Type=Story, родитель=Epic, статус по маппингу, содержимое — секции из `stories.md` (User flow, AC, Manual gate).
- **Создать Task под Story:** Type=Task, родитель=Story (не Epic), поля Priority/Estimate/Area/Iteration, Orchestration-блок в Notes.
- **Обновить статус:** изменить поле Status по маппингу.
- Трекер не даёт фильтр по property — загрузи список, фильтруй на стороне модели.

## DON'Ts

- **Не меняй structure / views / schema трекера.** Только содержимое страниц и стандартные поля.
- Не пиши в трекер без approve.
- Не считай трекер источником правды — это `stories.md` на диске.
- Не блокируй pipeline, если трекер недоступен — он опционален.
