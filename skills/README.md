# Универсальная библиотека скиллов продуктовой разработки

Переносимый набор из 34 скиллов: продуктовый pipeline (идея → проверка рынка → ценность → PRD → дизайн → код → тесты → деплой → аналитика) + standalone-скиллы (советники, юр-ревью, синк с трекером, маркетинг, утилиты). **Не привязан к конкретному проекту** — вся специфика в одном файле-анкете. Методология продуктовых шагов — канон NMT/AJTBD Замесина, читается в рантайме (`_shared/nmt-canon-routing.md`).

## Два принципа

**1. Один чат = одно исполнение скилла.** Скилл делает свою часть, кладёт артефакт на диск, готовит **готовый-к-вставке промпт** для следующего чата и просит открыть новый. Контекст не переполняется — каждый шаг стартает с чистого листа и читает артефакты с диска. Подробно — `_shared/handoff-protocol.md`.

**2. Ядро не зависит от внешних систем.** Бэклог, артефакты, статусы — всё в файлах репозитория (`DOCS_ROOT/`). Трекер задач (Notion/Linear/Jira) и юридическое ревью — **опциональные standalone-скиллы**, подключаются по необходимости, ядро без них полностью рабочее.

## Как устроено

```
skills/
├── README.md
├── _shared/                   ← общие протоколы, на которые ссылаются все скиллы
│   ├── project-config.md      ← ЕДИНСТВЕННЫЙ файл, который заполняется под проект
│   ├── mode.md                ← ось MODE (app/work — кто доводит до прода)
│   ├── tracks.md              ← ось TRACK (fast/prd/indie/enterprise)
│   ├── approve-protocol.md    ← когда нужен approve
│   ├── handoff-protocol.md    ← передача между чатами + единая карта pipeline
│   ├── chat-lifecycle.md      ← жизненный цикл чата
│   ├── backlog.md             ← формат файлового бэклога stories.md
│   ├── artifact-storage.md    ← где живут артефакты эпика
│   ├── communication-style.md ← бизнес-язык vs технический, zero-slop
│   ├── delivery-workflow.md   ← контракт авто-delivery (Workflow-сабагенты)
│   ├── executor-protocol.md   ← передача кодинга внешним исполнителям (task-packet)
│   ├── nmt-canon-routing.md   ← таблица «задача → файл канона NMT»
│   ├── landing-page-text.md   ← промпт-структура текста лендинга
│   ├── worktree-protocol.md   ← изоляция параллельных веток
│   └── templates/             ← шаблоны CLAUDE.md, summary, task-packet
└── <34 скилла>/SKILL.md (+ templates/)
```

## Продуктовый pipeline (19 скиллов)

Иерархия работы: **Epic → Story → Task**. Каждый шаг — отдельный чат, заканчивается хендофф-блоком. Единая карта маршрутизации — `_shared/handoff-protocol.md`.

**Вход и fast-трек:**

| Скилл | Что делает |
|---|---|
| `kickoff` | Роутер новой задачи: определяет, где она живёт, выбирает MODE и TRACK, отправляет в первый скилл |
| `mvp` | Fast-трек: короткий бриф → рабочий MVP или прототип за один заход, без discovery |

**Эпик-стадия:**

| Шаг | Скилл | Что делает |
|---|---|---|
| 0 *(опц.)* | `market-research` | Проверяет идею на прочность до PRD: сегменты, конкуренты по работам, pivot-опции; вердикт «стоит / рискованно / не стоит» с честным «нет» |
| 0.5 *(опц.)* | `craft-value-proposition` | Собирает сильнейшее ценностное предложение для сегмента: механики ценности по графу работ → RICE → RAT-карточки + спека для PRD |
| 1 | `epic-prd` | PRD эпика через интервью с владельцем; два шаблона — инженерный (machine) и для людей (human, формат X5) |
| 1.5 | `ux-patterns` | Выясняет, как это обычно делают: проверенные UI-паттерны → паттерн-контракт для прототипа |
| 2 | `epic-preview` | Кликабельный HTML-прототип — согласовать глазами до первой строчки кода (гейт ⏸) |
| 3 | `epic-tech-spec` | Техническая раскладка: схема данных, эндпоинты, потоки, события аналитики |
| 4 | `epic-arch-review` | Архитектурный вердикт go/no-go перед разработкой |
| 5 | `agile-coach decompose` | Режет эпик на Stories и Tasks в файловый бэклог `stories.md` |

**Story-стадия** (MODE=app; авто-оркестратор `delivery-run` гонит шаги 6–9 сабагентами сегментами между гейтами, ручной фоллбэк — по чату на скилл):

| Шаг | Скилл | Что делает |
|---|---|---|
| — | `delivery-run` | Авто-оркестратор delivery: цепочка build → review → test → docs сабагентами, остановки только на человеческих гейтах |
| 6 | `task-build` | Реализует одну Task в своей ветке — код, тесты, события аналитики |
| 7 | `task-cross-review` | Кросс-ревью: две модельные линзы (безопасность, соответствие AC) + машинные проверки |
| 8 | `task-test` | Тесты и e2e по критериям приёмки, ручной показ на prod-сборке (гейт ⏸) |
| 9 | `task-docs` | Документация: пользовательская, для support-агентов, реестр событий |
| 10 | `task-ship` | Финальный approve ⏸ → мерж → деплой → проверка здоровья → `done` в бэклоге |
| — | `dev-handoff` | MODE=work: вместо delivery-контура — каркас кода + README-пакет для живого разработчика |

**Замыкание / мета:**

| Скилл | Что делает |
|---|---|
| `analytics-insights` | Читает продуктовую аналитику и превращает метрики в гипотезы для следующего PRD |
| `pipeline-retro` | Ретро самого pipeline: режет токены, чинит скиллы |

`agile-coach` отдельно ведёт файловый бэклог: стендапы, груминг, приоритизация, WIP, auto-rollup статусов.

## Standalone-скиллы (15, вне pipeline — по запросу)

Не входят в хендофф-цепочку, вызываются вручную:

| Скилл | Что делает |
|---|---|
| `ask-nmt` | Разговорный продуктовый советник в методологии NMT/AJTBD: объяснит концепт, продиагностирует ситуацию, прожмёт гипотезу как скептичный сеньор-PM |
| `triz-resolve` | Решатель противоречий по ТРИЗ (адаптация под продукт): ИКР → противоречие → сильное решение вместо компромисса |
| `epic-legal-review` | Юридическое ревью эпика под режим проекта (РФ / GDPR / generic) — для эпиков с ПДн, платежами, рекламой |
| `tracker-sync` | Зеркалит файловый бэклог во внешний трекер: Notion / Linear / Jira / GitHub Issues |
| `todo` | Быстрый захват задач в GitHub Issues и на доску Taskboard: одной строкой или пачкой из свалки мыслей |
| `marketing-gtm` | Go-to-market: ICP, позиционирование, воронка привлечения, план запуска |
| `marketing-copywriting` | Слоганы, баннеры, тексты лендинга, офферы |
| `marketing-promotion` | Продвижение: выбор каналов, медиаплан, бюджеты, UTM-разметка |
| `marketing-smm` | SMM: рубрикатор, контент-календарь, посты под каналы |
| `video-distill` | Транскрипт видео или лекции → структурированный конспект, который читают другие скиллы |
| `watch` | Смотрит видео по ссылке: транскрипт + кадры по сменам сцен — видит, что показано на экране |
| `helpx5` | Полный цикл базы знаний help-центра X5 Транспорт: разбор материалов из Inbox → статьи → стенд |
| `go` / `goon` | Пара утилит фоновых сессий: увести задачу в живучий tmux-ран на сервере / вернуть итог в чат |
| `response-optimizer` | Фоновый хук качества ответов (SessionStart/UserPromptSubmit), руками не вызывается |

## Как подключить к проекту

1. **Скопируй библиотеку** в проект: `cp -r skills/* <project>/.claude/skills/` (или куда твоя среда подхватывает скиллы).
2. **Заполни `_shared/project-config.md`** — это вся адаптация. Раздел **ЯДРО** обязателен (продукт, стек, деплой, бэклог). **ОПЦИОНАЛЬНЫЕ МОДУЛИ** (аналитика, юр-режим, трекер, маркетинг) — только если подключаешь соответствующий скилл.
3. **Опционально — проектный `CLAUDE.md`** с правилами, специфичными для проекта.
4. Готово. Скиллы активируются по фразам-триггерам из их `description`.

Пока поле в `project-config.md` не заполнено — скилл, которому оно нужно, останавливается и спрашивает, а не угадывает.

## Где живёт состояние

- `DOCS_ROOT/<epic-slug>/` — PRD, preview, tech-spec, arch-review, market-research, `stories.md`
- `stories.md` — файловый бэклог эпика: Stories + Tasks + статусы + orchestration-граф. Источник правды, ведёт `agile-coach`.
- `DOCS_ROOT/<feature-slug>/` — user/support/analytics документация
- feature-ветки + git worktree'и — изоляция параллельных Story
- Трекер (если подключён `tracker-sync`) — зеркало для удобства просмотра, **не** источник правды

## Модели

Скиллы помечены `recommended_model` во frontmatter:
- **Opus** — где нужно думать (market-research, PRD, архитектура, код, декомпозиция, ревью, гипотезы, маркетинг-стратегия).
- **Sonnet** — шаблонная работа (preview по шаблону, тесты, документация, оркестрация деплоя, рутинный agile-coach, tracker-sync).

Два правила, из которых следует остальное ([executor-protocol.md](_shared/executor-protocol.md)):

1. **Качество кода задаёт пакет задачи, а не модель.** Красные тесты, контракт интерфейсов, узкий
   контекст и быстрая проверка влияют сильнее, чем выбор исполнителя. Task не получилась — сначала
   чини пакет, потом поднимай модель.
2. **`effort` нужен обратно пропорционально детерминированности проверки.** Есть красный тест —
   размышления добавляют мало; нет оракула (ревью, архитектура, непонятное падение) — размышление
   и есть работа.

Эскалация — лестницей, не фиксированным максимумом: попытка 1 на `medium`, ретрай после красного
`verify` на `high`, второй красный — ревизия пакета, а не третья попытка. Ревьюер **строго выше**
исполнителя.

**Передача кодинга вниз.** Написание кода можно отдать младшей модели или другому провайдеру:
проектирование (контракт интерфейсов + красные тесты) остаётся у топ-модели, реализация уходит
исполнителю с самодостаточным пакетом задачи, приёмка — скриптом и кросс-ревью.
Протокол — `_shared/executor-protocol.md`, шаблон — `_shared/templates/task-packet.md`,
замер исполнителей — `../tools/calibrate/`.
