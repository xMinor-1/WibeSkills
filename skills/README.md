# Универсальная библиотека скиллов продуктовой разработки

Переносимый набор из 32 скиллов: продуктовый pipeline (идея → проверка рынка → ценность → PRD → дизайн → код → тесты → деплой → аналитика) + standalone-скиллы (советники, юр-ревью, синк с трекером, маркетинг, утилиты). **Не привязан к конкретному проекту** — вся специфика в одном файле-анкете. Методология продуктовых шагов — канон NMT/AJTBD Замесина, читается в рантайме (`_shared/nmt-canon-routing.md`).

## Два принципа

**1. Один чат = одно исполнение скилла.** Скилл делает свою часть, кладёт артефакт на диск, готовит **готовый-к-вставке промпт** для следующего чата и просит открыть новый. Контекст не переполняется — каждый шаг стартает с чистого листа и читает артефакты с диска. Подробно — `_shared/handoff-protocol.md`.

**2. Ядро не зависит от внешних систем.** Бэклог, артефакты, статусы — всё в файлах репозитория (`DOCS_ROOT/`). Трекер задач (Notion/Linear/Jira) и юридическое ревью — **опциональные standalone-скиллы**, подключаются по необходимости, ядро без них полностью рабочее.

## Как устроено

```
│   ├── mode.md                ← ось MODE (app/work — кто доводит до прода)
│   ├── tracks.md              ← ось TRACK (fast/prd/indie/enterprise)
│   ├── approve-protocol.md    ← когда нужен approve
│   ├── handoff-protocol.md    ← передача между чатами + единая карта pipeline
│   ├── chat-lifecycle.md      ← жизненный цикл чата
│   ├── backlog.md             ← формат файлового бэклога stories.md
│   ├── artifact-storage.md    ← где живут артефакты эпика
│   ├── communication-style.md ← бизнес-язык vs технический, zero-slop
│   ├── delivery-workflow.md   ← контракт авто-delivery (Workflow-сабагенты)
│   ├── executor-protocol.md   ← передача кодинга внешним исполнителям (task-packet)
│   ├── nmt-canon-routing.md   ← таблица «задача → файл канона NMT»
│   ├── landing-page-text.md   ← промпт-структура текста лендинга
│   ├── worktree-protocol.md   ← изоляция параллельных веток
│   └── templates/             ← шаблоны CLAUDE.md, summary, task-packet
└── <32 скилла>/SKILL.md (+ templates/)
```

## Продуктовый pipeline (19 скиллов)

Иерархия работы: **Epic → Story → Task**. Каждый шаг — отдельный чат, заканчивается хендофф-блоком. Единая карта маршрутизации — `_shared/handoff-protocol.md`.

**Вход и fast-трек:**
- `kickoff` — entry-router: где живёт задача, MODE+TRACK → `epic-meta.md` → первый скилл
- `mvp` — fast-трек: бриф → код/прототип за один заход, без discovery

**Эпик-стадия:**
- 0. `market-research` *(опц.)* — проверка идеи на прочность: карта сегментов с selection screen, конкуренты по работам, клин, pivot-опции под активы, RAT; вердикт ✅/⚠️/❌
- 0.5 `craft-value-proposition` *(опц.)* — генерация ценностного предложения: механики ценности по графу работ → фильтр → RICE → primary + RAT-карточки + спека для PRD
- 1. `epic-prd` — PRD на эпик через интервью
- 1.5 `ux-patterns` — исследование устоявшихся UI/UX-паттернов → паттерн-контракт для preview + накопительная база паттернов проекта
- 2. `epic-preview` — статичный HTML-прототип = эталон UI (визуальный гейт ⏸)
- 3. `epic-tech-spec` — техническая раскладка
- 4. `epic-arch-review` — арх-вердикт go/no-go
- 5. `agile-coach decompose` — Эпик → Stories → Tasks в файл `stories.md`

**Story-стадия** (MODE=app; авто-оркестратор `delivery-run` гонит шаги 6–9 сабагентами сегментами между гейтами, ручной фоллбэк — по чату на скилл, все Tasks Story в одном worktree):
- 6. `task-build` — реализация одной Task в feature-ветке
- 7. `task-cross-review` — две модельные линзы (безопасность/юр-режим, соответствие AC) + машинные проверки
- 8. `task-test` — unit + e2e на prod-build + Story manual gate ⏸
- 9. `task-docs` — user / support / analytics документация
- 10. `task-ship` — финальный approve ⏸ → деплой → smoke → бэклог `done`

**MODE=work:** вместо delivery-контура — `dev-handoff`: каркас кода + README-пакет для живого разработчика.

**Замыкание / мета:**
- `analytics-insights` — данные → гипотезы → вход в следующий PRD
- `pipeline-retro` — ретро на сам pipeline, режет токены

`agile-coach` отдельно ведёт файловый бэклог: стендапы, груминг, приоритизация, декомпозиция, auto-rollup статусов.

## Standalone-скиллы (13, вне pipeline — по запросу)

Не входят в хендофф-цепочку, вызываются вручную:
- `ask-nmt` — разговорный советник по методологии NMT/AJTBD: объясняет концепты, диагностирует продуктовую ситуацию, прожимает гипотезы, роутит в скиллы-продюсеры. Входная дверь пайплайна.
- `triz-resolve` — разговорный решатель изобретательских задач по ТРИЗ Альтшуллера (адаптирована под продукт): ИКР → противоречие → разделение + 40 приёмов → ресурсы. Даёт разрешение конфликта, а не компромисс. Метод в `triz-resolve/references/triz-toolkit.md`.
- `epic-legal-review` — юр-ревью эпика (regime-aware: РФ / GDPR / generic). Вызывается для эпиков с юридической поверхностью (ПДн, платежи, реклама, договоры).
- `tracker-sync` — мост между файловым бэклогом и внешним трекером (Notion/Linear/Jira). Допиливается под конкретный трекер.
- `marketing-copywriting` — слоганы, баннеры, лендинг-копия, офферы
- `marketing-smm` — рубрикатор, контент-календарь, посты под каналы
- `marketing-promotion` — выбор каналов, медиаплан, бюджеты, UTM
- `marketing-gtm` — ICP, позиционирование, ценностное предложение, план запуска
- `video-distill` — транскрипт видео/лекции → структурированный конспект для других скиллов
- `helpx5` — полный цикл базы знаний help-центра X5 Транспорт: Inbox → статьи → стенд
- `go` / `goon` — пара утилит фоновых сессий: увести задачу в живучий tmux-ран / вернуть итог в чат
- `response-optimizer` — хук-скилл (SessionStart/UserPromptSubmit), руками не вызывается

## Как подключить к проекту

1. **Скопируй библиотеку** в проект: `cp -r skills/* <project>/.claude/skills/` (или куда твоя среда подхватывает скиллы).
2. **Заполни `_shared/project-config.md`** — это вся адаптация. Раздел **ЯДРО** обязателен (продукт, стек, деплой, бэклог). **ОПЦИОНАЛЬНЫЕ МОДУЛИ** (аналитика, юр-режим, трекер, маркетинг) — только если подключаешь соответствующий скилл.
3. **Опционально — проектный `CLAUDE.md`** с правилами, специфичными для проекта.
4. Готово. Скиллы активируются по фразам-триггерам из их `description`.

Пока поле в `project-config.md` не заполнено — скилл, которому оно нужно, останавливается и спрашивает, а не угадывает.

## Где живёт состояние

- `DOCS_ROOT/<epic-slug>/` — PRD, preview, tech-spec, arch-review, market-research, `stories.md`
- `stories.md` — файловый бэклог эпика: Stories + Tasks + статусы + orchestration-граф. Источник правды, ведёт `agile-coach`.
- `DOCS_ROOT/<feature-slug>/` — user/support/analytics документация
- feature-ветки + git worktree'и — изоляция параллельных Story
- Трекер (если подключён `tracker-sync`) — зеркало для удобства просмотра, **не** источник правды

## Модели

Скиллы помечены `recommended_model` во frontmatter:
- **Opus** — где нужно думать (market-research, PRD, архитектура, код, декомпозиция, ревью, гипотезы, маркетинг-стратегия).
- **Sonnet** — шаблонная работа (preview по шаблону, тесты, документация, оркестрация деплоя, рутинный agile-coach, tracker-sync).

Два правила, из которых следует остальное ([executor-protocol.md](_shared/executor-protocol.md)):

1. **Качество кода задаёт пакет задачи, а не модель.** Красные тесты, контракт интерфейсов, узкий
   контекст и быстрая проверка влияют сильнее, чем выбор исполнителя. Task не получилась — сначала
   чини пакет, потом поднимай модель.
2. **`effort` нужен обратно пропорционально детерминированности проверки.** Есть красный тест —
   размышления добавляют мало; нет оракула (ревью, архитектура, непонятное падение) — размышление
   и есть работа.

Эскалация — лестницей, не фиксированным максимумом: попытка 1 на `medium`, ретрай после красного
`verify` на `high`, второй красный — ревизия пакета, а не третья попытка. Ревьюер **строго выше**
исполнителя.

**Передача кодинга вниз.** Написание кода можно отдать младшей модели или другому провайдеру:
проектирование (контракт интерфейсов + красные тесты) остаётся у топ-модели, реализация уходит
исполнителю с самодостаточным пакетом задачи, приёмка — скриптом и кросс-ревью.
Протокол — `_shared/executor-protocol.md`, шаблон — `_shared/templates/task-packet.md`,
замер исполнителей — `../tools/calibrate/`.
