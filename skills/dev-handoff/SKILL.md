# Dev Handoff

Финальный шаг **work-контура**: превращаешь продуктовую проработку (PRD + прототип + спека) в
**самодостаточный пакет**, который живой программист берёт и доводит до прода. Ты не мержишь, не
гоняешь полный pipeline тестов и не деплоишь в прод — это делает человек.

Контекст — `../_shared/project-config.md` + проектный `CLAUDE.md`. Режимы — `../_shared/mode.md`. Approve — `../_shared/approve-protocol.md`. Шаблон README пакета — `templates/handoff-readme.md`.

## Режим (work-only)

Прочитай `MODE` — `../_shared/mode.md`. Этот скилл для `work`. Если `MODE: app` (или проект ведётся полностью мной) — скажи одной строкой, что в app-режиме код доводится через `task-build → task-ship`, и предложи их. Жди решения.

## Старт

Approve **не нужен** для сборки пакета (он не трогает прод). Approve/⏸ **нужен**, только если по ходу
просят выкатить пакет на боевой (`cms.wibecodex5t.ru`, Strapi) — это ручной гейт владельца.

## Шаг 1: Собери вход

Найди и прочитай, что уже есть по эпику (не выдумывай заново):
- **PRD** (`DOCS_ROOT/<эпик>/PRD.md` или указанный в обсуждении) — что и зачем делаем.
- **Прототип** (`epic-preview` HTML / макет) — как выглядит, какие CSS-переменные/классы.
- **tech-spec** (`epic-tech-spec` в work-режиме — спека для разработчика) — схема, эндпоинты, события.

Чего-то нет — не блокируйся: либо собери из текущего обсуждения, либо предложи добежать
недостающий шаг (`epic-prd` / `epic-preview` / `epic-tech-spec`). Скажи, что берёшь как вход.

## Шаг 2: Зафиксируй целевой стек и инфру

Из инфра-блока `project-config.md`:
- стек, на который ляжет результат (для x5 по умолчанию: Next.js App Router + Strapi);
- куда это в итоге поедет (`cms.wibecodex5t.ru`, codehost), какие env/секреты нужны;
- **паттерн безопасности handoff** (эталон — `freight-map-handoff`): Strapi закрыт от Public,
  токен только серверный (`process.env`), авторизация httpOnly cookie + HMAC, вставка текста
  только через JSX (без `innerHTML`). Применяй его, если пакет трогает данные/авторизацию.

## Шаг 3: Собери пакет `<slug>-handoff/`

Папка рядом с продуктом (`DOCS_ROOT/<эпик>/<slug>-handoff/` или в папке профильного продукта).
Содержимое — по `templates/handoff-readme.md`. Минимум:
- **README.md** — главный документ: что внутри → установка по шагам → env → слияние с существующим
  кодом → архитектурные решения (FYI) → тесты после установки → что НЕ сделано (вне scope).
- **Каркас кода** — структура файлов, типы, pure-функции, API-route контракты, схема Strapi
  (`schema.json`). Это рабочий скелет под доводку, а не финальный прод-код: помечай `TODO` там,
  где программист должен принять решение или дописать бизнес-логику.
- **`.env.example`** — все переменные с комментариями; реальные секреты не клади.

Правило: пакет должен запускаться по README **без тебя**. Каждое неочевидное решение —
короткий абзац «почему так» в секции FYI (как в эталоне freight-map).

## Шаг 4: Подстраховка (work-режим)

- Если каркас собирается/прогоняется (`npm run build`, скрипт) — прогони **один smoke** и почини
  очевидное. Полный pipeline тестов не нужен.
- Покажи владельцу: что в пакете, что программист должен доделать, что вне scope. Дождись ✅.
- Боевой деплой пакета — **только** ручной гейт владельца, сам не выкатывай.

## Выход

Короткое резюме на бизнес-языке:
> Пакет `<slug>-handoff/` готов к передаче. Программист: ставит по README (`<N>` шагов), env `<...>`,
> доделывает `<список TODO / вне scope>`. Что уже решено за него: `<ключевые архитектурные решения>`.

Это не pipeline-хендофф в новый чат — work-контур заканчивается готовым пакетом.
