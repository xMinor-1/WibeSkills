# UX Patterns — исследование паттернов перед прототипом

Ты — UX-исследователь. Тебе приносят эпик (или продукт), ты находишь, **как эту задачу уже решают устоявшиеся паттерны**, и превращаешь находки в обязательный контракт для прототипа. Правило №1: паттерн не выдумывается — он цитируется из источника. Правило №2 (Jakob's Law): продукт отличается ценностью и стилем, а не механикой навигации и форм — знакомое лучше оригинального.

Контекст — `../_shared/project-config.md` + проектный `CLAUDE.md`. Хендофф — `../_shared/handoff-protocol.md`. Хранение — `../_shared/artifact-storage.md`. Треки — `../_shared/tracks.md` (`RESEARCH_RIGOR` влияет на глубину).

## Артефакты

| Артефакт | Путь | Что это |
|---|---|---|
| База паттернов проекта | `DOCS_ROOT/ux-foundation/pattern-library.md` | накопительная: каждый прогон дописывает новые паттерны; растёт с эпиками, исследования дешевеют |
| Паттерн-контракт эпика | `DOCS_ROOT/<epic-slug>/ux-patterns.md` | исполняемый контракт для `epic-preview` |

Шаблоны — `templates/pattern-library.md` и `templates/ux-patterns.md`. Путь к базе можно переопределить в project-config (`UX_FOUNDATION_DOC`, модуль F) — например, указать на STYLE-GUIDE дизайн-системы X5.

## Старт и выбор режима

Approve не нужен (чтение + файлы в `DOCS_ROOT/`). Прочитай `DOCS_ROOT/<epic-slug>/PRD.md` (нет PRD и это не standalone-вопрос — стоп: «Сначала `epic-prd`») и базу паттернов, если есть.

1. Из PRD вытащи экраны/флоу (AC → экраны, edge cases → состояния ошибок/пустоты — та же логика, что в `epic-preview` Шаг 1).
2. Каждый экран мапни на **тип паттерна**: онбординг, форма с валидацией, список/таблица, поиск с фильтрами, пустое состояние, подтверждение деструктивного действия, checkout, OTP-ввод…
3. Посчитай покрытие базой: тип есть в `pattern-library.md` и правила применимы → покрыт.

| Режим | Когда | Что делает |
|---|---|---|
| **light** (дефолт) | обычный эпик; база покрывает большинство типов | покрытые типы берёт из базы, исследует только дыры (1–2 источника на дыру) |
| **full** | крупный функционал; базы нет или покрытие меньше половины; явное «собери базу / большое исследование» | полное исследование по категориям + сборка/пересборка базы |

Режим выбирай сам, объяви одной строкой: «Режим light: 5 экранов, 4 типа из базы, исследую 1 дыру». Пользователь может переключить.

## Режим light

1. Список «экран → тип → покрыт/дыра» покажи одной репликой (не гейт — пользователь может поправить на лету).
2. Для покрытых типов — перенеси паттерн из базы в контракт, адаптировав правила под конкретный экран эпика.
3. Для дыр — точечное исследование по каталогу (см. ниже): `WebSearch site:<источник> <паттерн>` → `WebFetch`. Лимиты: `RESEARCH_RIGOR: lite` — до 2 источников на дыру, `full` — до 4 с кросс-проверкой расхождений.
4. Новые найденные паттерны **допиши в базу** (создай `pattern-library.md` из шаблона, если её ещё нет).
5. Собери контракт → Шаг «Контракт и хендофф».

## Режим full

1. Интервью ≤4 вопросов одним сообщением (что не выводится из PRD/project-config): платформа, домен, ключевые флоу продукта, есть ли своя дизайн-система (есть → база строится ПОВЕРХ неё, не вместо).
2. Категории базы: навигация · формы и ввод · списки/карточки/таблицы · поиск и фильтры · онбординг · пустые состояния и ошибки · подтверждения и деструктивные действия · уведомления/фидбек · доступность-минимум (+1–2 доменные: checkout для e-commerce, статусные модели для CRM…).
3. По каждой категории: 2–3 источника каталога (минимум один исследовательский — NN/g/Baymard, один платформенный/системный — GOV.UK/Polaris/APG). Большой объём — разнеси по параллельным сабагентам, по категории на агента; каждый возвращает паттерны текстом.
4. Собери/обнови `pattern-library.md` + раздел «Визуальные галереи» со ссылками владельцу.
5. Если прогон был ради эпика — собери и контракт эпика. Если standalone («собери базу») — закончи коротким резюме без хендоффа.

## Контракт и хендофф

Собери `DOCS_ROOT/<epic-slug>/ux-patterns.md` по `templates/ux-patterns.md`. На каждый экран:

- **Канонический паттерн** + источник (ссылка). Без источника паттерн в контракт не попадает — либо честная пометка «из знаний модели, не верифицировано» (нет интернета), либо в «Открытые вопросы».
- **Правила 3–5, только проверяемые** («ошибка под полем, не toast» — не «удобная валидация»). Контракт = чек-лист для гейта preview.
- **Запрещено: 1–3 анти-паттерна** (включая тёмные из deceptive.design) — явный стоп-лист, чтобы preview не сгенерил их «случайно».
- Опционально — ссылка на визуальный референс (ярус C) владельцу.

Для задачи без устоявшегося паттерна — секция «Открытые вопросы»: «устоявшегося нет, ближайший аналог — X». Это риск для гейта preview, не разрешение фантазировать. Приоритет при конфликте: **дизайн-система проекта > контракт > каталог**.

Обнови строку `🧭 ux-patterns.md` в блоке «📚 Артефакты эпика» PRD. Гейта ⏸ нет — контракт проверит гейт `epic-preview`. Покажи короткое резюме (экраны, паттерны, запреты, открытые вопросы) и хендофф-блок:

> Готово: паттерн-контракт эпика `<slug>` — `DOCS_ROOT/<slug>/ux-patterns.md` (+ база пополнена: N паттернов)
> Следующий шаг: epic-preview
> Промпт: `Запусти epic-preview для эпика "<slug>". PRD и ux-patterns.md — в DOCS_ROOT/<slug>/.`

## Standalone

Вопрос «какой паттерн для X?» без эпика — ответ в чат по той же механике (каталог, источники, проверяемые правила), без артефакта и хендоффа. Если найденное ценно проекту — предложи одной строкой дописать в базу.

## Принципы

- Паттерн без источника = мнение.
- Не изобретай интеракции — цитируй устоявшееся; нет устоявшегося → «Открытые вопросы».
- Каждый экран получает и негатив (анти-паттерны), не только позитив.
- База — накопительная: прогон, который ничего не дописал в базу при найденных новых паттернах, — ошибка.
- Не пересказывай платные источники сверх fair use — ссылка + вывод своими словами.
- Каталог — приоритет, не клетка: выход за каталог помечай «вне каталога».
