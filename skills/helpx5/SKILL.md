# helpx5 — цикл пользовательской документации

Один прогон = «посмотрел, что нового → превратил в статьи → обновил базу под них →
привёл в порядок картинки → залил → проверил, что читателю всё видно». Состояние живёт
в файлах, поэтому прогон можно прервать и продолжить.

## Режимы вызова

| Команда | Что делает |
|---|---|
| `/helpx5` | полный прогон: новые материалы → статьи → структура → заливка → проверка |
| `/helpx5 проверка` | только шаг 7: сплошная проверка сайта, ничего не меняет |
| `/helpx5 картинки` | только шаг 5: обрезка и ретушь скриншотов + перезаливка ссылок |
| `/helpx5 структура` | только шаг 6: привести площадку к `target-structure.json` |
| `/helpx5 пакет` | собрать пакет для передачи на прод X5 (шаг 8) |
| `/helpx5 <вопрос>` | точечная правка по просьбе владельца — идти прямо в нужный шаг |

Владелец часто формулирует задачу словами («подрежь скриншоты», «перепиши раздел короче») —
это тот же конвейер, просто с одного шага. Полный прогон вхолостую не гонять.

## Контур

| Что | Где |
|---|---|
| Входящие материалы | Я.Диск `disk:/Материал базы знаний/Inbox` (владелец xMinor1) |
| Архив обработанного | `disk:/Материал базы знаний/Inbox/_Архив/<ГГГГ-ММ-ДД>` |
| Токены | `~/.config/yandex-disk-token`, `~/.config/helpx5-cms-token` (600, вне репо) |
| Скрипты | `~/Work/strapi-bg/tools/helpx5/` |
| Мозг базы | `Help-центр/knowledge-base/` — реестр, мастер-копии статей, медиа, бэкапы |
| Кэш материалов (тяжёлый, вне Syncthing) | `~/helpx5-cache/` |
| Стенд | CMS https://cms.wibecodex5t.ru · фронт https://help.wibecodex5t.ru/help |
| Снимок боевой базы X5 | `knowledge-base/prod/` — 42 статьи, manifest.json с documentId |
| Пакет для прода | `~/Work/2. Outbox/helpx5-prod-<дата>/` |

Источники правды, которые нельзя менять по своему усмотрению:
`knowledge-base/target-structure.json` (разделы, порядок, состав, аудитория, цепочки),
`STRUKTURA-na-soglasovanie.md` (та же структура словами, с обоснованием),
`skills/helpx5/article-rules.md` (конвенция и стиль статьи),
`pravki-fronta.md` (что нельзя починить из админки — уходит разработчику X5).

## Прогон

### Шаг 1. Что нового

```bash
cd ~/Work/strapi-bg/tools/helpx5
python3 ydisk.py scan            # сверка Inbox с реестром
python3 ydisk.py pull            # в ~/helpx5-cache/raw/
python3 extract.py               # html/pdf/docx/zip → markdown + картинки
nohup python3 video.py --all > ~/helpx5-cache/video-run.log 2>&1 &   # видео: долго, в фон
```

Сторож `watch-inbox.sh` ежечасно делает то же сам и оставляет заявку в
`~/.claude/helpx5-pending.md` — загляни туда, там список приехавшего.
Ключ материала — md5 (для папок отпечаток содержимого), папка верхнего уровня = один материал.
Нет нового — сказать это и остановиться.

### Шаг 2. Разобрать материалы

`video.py` — это метод **/watch** на локальных файлах: транскрипт Whisper + кадры по сменам
сцен. Кадры обязательно просмотреть глазами: в записях экрана смысл в интерфейсе, а не в звуке.

Мало кадров (запись 20+ минут дала пару десятков) — сцена не менялась при прокрутке формы.
Донарезать равномерно, иначе половина экранов останется без скриншотов:

```bash
ffmpeg -i <видео> -vf "fps=1/12,scale=1600:-2" -q:v 3 <папка>/frames-grid/t_%04d.png
```

Разборы кэшируются в `knowledge-base/digests/<md5>.json` — перед разбором проверить, нет ли
готового.

### Шаг 3. Снять текущую базу

```bash
python3 cms.py pull              # статьи и категории → knowledge-base/articles/*.md
python3 cms.py status            # что разошлось между файлами и CMS
```

### Шаг 4. Написать статьи — Workflow

Материалы независимы, поэтому разбор и письмо гоним веером агентов:

```
Workflow({ scriptPath: "<скилл>/workflow.js", args: { materials: [...], day: "<дата>" } })
```

- md5 брать из `ydisk.py materials`, не из вывода `scan` (там первые 8 знаков);
- фазы: разбор (агент на материал) → план (один) → письмо (агент на статью) → ревью;
- на 4 ядрах одновременно бегут 2 агента — это нормально, остальные ждут очереди;
- слияния и переписывание разделов — тем же способом, по агенту на статью, с правилом
  из `article-rules.md` в промпте.

Восстановить путь пользователя по видео и пересобрать под него структуру — `workflow-cjm.js`.

### Шаг 5. Картинки

```bash
python3 crop_shots.py <папка|файл>            # пробный прогон: что и насколько обрежется
python3 crop_shots.py knowledge-base/media --apply
python3 retouch.py scan                       # персональные данные на кадрах
python3 retouch.py apply                      # закрасить, перезалить, переставить ссылки
python3 recrop_shots.py --backup backups/crop-shots-<дата>   # чинит пережатые кадры
```

`crop_shots` снимает адресную строку и вкладки браузера, панель задач ОС и пустые поля вокруг
контента. Вертикальные кадры телефона сверху не режет — там шапка экрана, а не браузер.
Красную рамку-выделение и тёмную шапку кабинета, на которую рамка показывает, не трогает.
Результат обязательно посмотреть: автоматика ошибается на нестандартных макетах.

`retouch` распознаёт текст кадра вместе с координатами (tesseract tsv) и закрашивает почты,
телефоны, ФИО, ИНН и названия реальных компаний плашкой цвета фона. Служебные ящики
платформы и демо-названия остаются — они читателю нужны. Личная почта сотрудника
(`имя.фамилия@x5.ru`) — персональные данные, её закрашиваем.

`recrop_shots` пересобирает кадры из оригиналов в `backups/crop-shots-<дата>`, когда обрезка
съела рамку или навигацию вокруг неё. Запускать после любых жалоб «на скриншоте не видно кнопку».

**Ширина кадра задаётся маркером `|w=` в подписи** — `![подпись|w=320](url)`. Без него
картинка тянется на всю колонку: снимок телефона выходит выше экрана читателя. Ширину
считать от высоты: `w = 520 * ширина / высота`, но не больше 320 для снимков телефона.

Все картинки перезаливать **под новым именем**: они отдаются с годовым кэшем, подмена файла
по старому адресу до читателя не дойдёт. Ссылки в телах статей переставлять и в CMS,
и в мастер-копиях на диске (это делают `retouch`/`recrop_shots` сами).

### Шаг 6. Структура

```bash
python3 apply_structure.py --dry-run      # что изменится
python3 apply_structure.py
```

Приводит площадку к `target-structure.json`: разделы с описаниями и порядком, раскладка
статей с порядком внутри раздела, аудитория, снятие поглощённых слиянием, удаление
опустевших разделов, цепочки на главной. Менять структуру — значит править json, а не CMS руками.

### Шаг 7. Залить и проверить

Заливка: PUT/POST в `/api/articles`, картинки — через `/api/upload`, дата `last_reviewed_at`
обязательна (без неё читатель видит статью без даты обновления).

**Кэш фронта рестартом контейнера не сбрасывается** — готовые страницы лежат в `web/.next/cache`
на диске и переживают перезапуск. Читатель после этого видит старую статью и решает, что правки
не доехали. Правильно:

```bash
cd ~/Work/strapi-bg
sudo docker compose stop web && sudo rm -rf web/.next/cache && sudo docker compose start web
# затем прогреть: пройтись curl по всем /help/article/<слаг>, разделам и главной — два раза
```

Заголовки кэша заданы в `Caddyfile`: страницы отдаются с `max-age=0, must-revalidate`
(иначе браузер держит свою копию по `stale-while-revalidate` на год), картинки —
`immutable` на год, поэтому меняем их только заливкой нового файла.

```bash
python3 verify_site.py --site https://help.wibecodex5t.ru
python3 check_blocks.py                   # правило блоков «Веб-ЛК / Приложение»
```

`verify_site.py` проверяет: страницы отдают 200, каждая картинка отдаётся, внутренние ссылки
ведут на существующие статьи, относительных ссылок не осталось, у разделов есть описания.
Прогон должен заканчиваться «Проблем нет» — иначе чинить и повторять.

### Шаг 8. Пакет и архив

```bash
python3 package_prod.py build             # пакет для боевой базы X5
python3 link.py                           # кто из какого материала вырос
python3 ydisk.py archive --used           # обработанное → Inbox/_Архив/<дата>
```

Пакет самодостаточен для слабой модели: `changes.json` с `documentId`, `articles/`,
`media/<слаг>/`, `AI-ZALIVKA.md`, `CHANGES.md`, `sources.md`. Заливать пакет умеет
`push_package.py`.

**Разобранный материал сразу уезжает в архив** (решение владельца 13.08.2026): статьи
написаны — `ydisk.py archive --used`. В Inbox остаётся только то, что ещё не разбирали,
иначе материал берут в работу второй раз. В конце прогона проверить `state.json`:
статусов `used` остаться не должно, все обработанные — `archived`.

Карта связей пересобирается здесь же:

```bash
python3 graph.py                      # graph.json + GRAPH.md
python3 graph.py --dupes              # материал уже разбирали в составе другого?
python3 graph.py --stale              # статьи по устаревшей версии материала
```

### Шаг 9. Карта связей

```bash
python3 graph.py                             # пересобрать graph.json и GRAPH.md
python3 graph.py --what "Услуги и сервисы"   # где упомянут элемент интерфейса
python3 graph.py --deps poisk-zayavok        # кто ссылается на статью, чем делится
python3 graph.py --source "Инструкция МП"    # что выросло из материала, с локаторами
python3 graph.py --stale                     # статьи по устаревшей версии материала
python3 graph.py --dupes                     # материал уже разбирали в составе другого
```

Пересобирать **после каждой волны правок** и **перед актуализацией**: карта отвечает на
вопрос «что ещё поедет», без неё правка ищется грепом. Индексируются связи статья↔статья,
элемент интерфейса → статьи, картинка → статьи, контакты → статьи, исходник → статьи
с локаторами (тайм-код, страница, раздел вики) и версии исходников.

Материал опознаётся отпечатком содержимого: пришёл повторно — виден как разобранный,
даже под другим именем. Файл внутри выгрузки ищется наравне с материалом целиком.
Имена сравниваются в одной нормализации Unicode: с macOS «й» приезжает как «и» + знак
краткости, и обычный поиск такое имя не находит.

## Правила контента

Полностью — в `article-rules.md`, здесь главное:

- **Один шаг — одно действие**, повелительное наклонение, язык пользователя, а не системы.
- **Веб-ЛК первым.** Блоки `## Веб-ЛК` и `## Приложение` содержат только различия поверхностей;
  общее (условия, ограничения, итог, куда идти дальше) выносится до блоков или после них
  за разделителем `---`. Одна фраза в двух блоках — ошибка.
- **Раздел «Регистрация и вход» — исключение:** там блоков нет, сплошной поток, потому что
  путь один и он в вебе (решение владельца 12.08.2026).
- **Короче.** Инструкция 150–350 слов, обзорная до 450. Всё, что человек видит на экране,
  пересказывать не надо.
- **Ничего не выдумывать.** Нет в материале — нет в статье; пробел идёт в отчёт как
  «нужен материал», а не дописывается по догадке.
- **Терминов системы избегать.** Владелец отдельно забраковал слово «мастер» — пишем
  «шаги регистрации», «вверху видно, какой шаг идёт».
- **Внутренняя кухня наружу не идёт.** SAP, ОРД, ТОРГ, ЕДЦ и статусы вида «Не согласован SAP» —
  это про устройство компании, а не про работу перевозчика. Если статус или система не видны
  пользователю в интерфейсе, в статье их нет. Проверять по скриншотам, а не по прод-тексту:
  часть боевых статей писалась изнутри и такие вещи в них просочились.
- **Ссылки только на свои статьи** — `/help/article/<слаг>`. Ссылка на `x5transport.ru/help/...`
  уводит читателя с площадки, а на стенде ведёт в никуда; `verify_site.py` такие ловит.
  Ссылка на сам сервис (кабинет, портал поддержки) — можно.
- **Переключатели вместо повторов.** `## Таб: <Название>` собирает подряд идущие секции
  в группу вкладок (легаси-имена `## Веб-ЛК` и `## Приложение` работают так же). Если статья
  описывает несколько равноправных путей — способы взять груз, роли, тарифы, — это вкладки,
  а не четыре подряд идущих раздела с одинаковыми шагами.
- **Вопросы в FAQ — про то, чего нет в теле.** «Где раздел „Деньги“?» — не вопрос, а навигация:
  ей место в тексте статьи. В FAQ идут ошибки, сроки, исключения, контакты.

## Что важно не сломать

- **Прод X5 не трогаем** — работаем на стенде, на прод изменения едут пакетом через разработчика.
- **Ничего не удалять в CMS без бэкапа.** `DELETE /api/articles/<id>` сносит документ целиком
  (флаг `?status=published` публикацию не снимает). Перед удалением сохранить тело в `backups/`.
- **Служебные элементы на скриншотах ретушируем, а не отрезаем.** Вкладку «Debug» в нижней
  панели приложения нельзя убрать обрезкой по ширине: уйдёт правый край экрана — теги и края
  кнопок. Правильно — закрасить пятую ячейку панели, скопировав соседнюю пустую колонку той же
  панели. Автопоиск панели по яркости ненадёжен: координаты задавать по конкретному кадру
  и проверять результат — в зоне ярлыка не должно остаться тёмных пикселей, соседняя вкладка
  должна уцелеть.
- **Персональные и боевые данные на кадрах** (имена участников звонка, почты, телефоны,
  реальные контрагенты, контакты менеджера) закрашивать цветом фона, а не чёрным
  прямоугольником — страница должна выглядеть естественно. Тестовые названия компаний
  владелец оставлять разрешил.
- **Структуру держать данными**, а не руками: `target-structure.json` → `apply_structure.py`.
  Порядок внутри важен: сначала разделы, потом раскладка статей, и только затем удаление
  поглощённых — иначе статья на миг остаётся без раздела и пропадает из навигации.
- **После слияний чинить ссылки.** Поглощённая статья исчезает, ссылки на неё остаются
  в соседях. Держать таблицу «старый слаг → приёмник» и прогонять замену по всей базе.
- **Кадры смотреть субагентами, если сессия уже полна картинок.** После нескольких десятков
  изображений API перестаёт принимать новые в этой сессии («many-image requests»), уменьшение
  файла не помогает. Раздать кадры агентам через Workflow — у каждого свой контекст.
- **`cms.py pull` — только до заливки.** После push он затянет статьи с абсолютными ссылками
  на картинки и затрёт локальные имена в мастер-копиях.
- **Токены не писать в файлы** репозитория, включая `state.json` и пакеты.
- Кэш `~/helpx5-cache/` держать вне `~/Work` — Syncthing разнесёт сотни мегабайт на ноутбук.
- Ничего не удалять командой `rm` — только перемещением в `backups/` или `archive/_trash-<дата>/`.

## Что докладывать владельцу отдельно

Прогон почти всегда находит то, что решает человек, а не агент:

- **скриншоты, которых нет** — экраны, не попавшие в запись; их надо доснять, а не рисовать;
- **персональные и боевые данные** на кадрах, если ретушь спорная или данных слишком много;
- **расхождения между материалами и базой** — разные сроки, названия кнопок, контуры процесса;
- **новые роли и разделы** — заводить раздел под новую аудиторию только с согласия;
- **правки, которые нельзя сделать из админки** — они копятся в `pravki-fronta.md`.
