# Epic Tech Spec

Превращаешь PRD + preview в **технический план**, по которому можно начинать декомпозировать. Без архитектурного вердикта (это шаг 4 — `epic-arch-review`).

Контекст — `../_shared/project-config.md` + проектный `CLAUDE.md`. Approve — `../_shared/approve-protocol.md`. Хендофф — `../_shared/handoff-protocol.md`. Хранение артефактов — `../_shared/artifact-storage.md`.

## Старт

Approve **не нужен**. Иду делать.

## Шаг 1: Контекст

1. Читай `DOCS_ROOT/<epic-slug>/PRD.md` (обязательно) и `preview/index.html` (если есть). Чего-то нет — стоп, скажи запустить предыдущий скилл.
2. Параллельно изучи существующий код в `CODE_ROOT`:
   - папки фич в стиле `ARCH_PATTERN` — какие фичи уже есть
   - схема `DB` — какие таблицы существуют
   - компоненты — что переиспользовать

Нужно глубокое исследование — subagent `feature-dev:code-explorer`.

Сомневаешься в текущей форме API библиотеки стека — Context7 MCP за свежими доками (если подключён). Не для базовых вещей.

## Шаг 2: Создание tech-spec.md

Прочитай `templates/tech-spec.md`. Создай `DOCS_ROOT/<epic-slug>/tech-spec.md` по структуре шаблона.

## Шаг 3: Опора на существующий код

- Не выдумывай паттерны — посмотри как сделаны похожие фичи (`ARCH_PATTERN`).
- Новая фича = новая папка по `ARCH_PATTERN`.
- Паттерн противоречит Clean Architecture — отметь в «Риски» для arch-review, **не правь сейчас**.
- Схему `DB` — расширяй существующие файлы, не дублируй.

## Шаг 4: Архитектурные подходы и паттерны

Заполняй секцию **осознанно**:

- **SOLID** — только те принципы, которые в этом эпике дают конкретную выгоду. Не применим — «не применимо» и почему. Не растягивай таблицу искусственно.
- **Паттерны** — выбирай из реальных болей: Repository (изоляция ORM), Strategy (несколько алгоритмов с одной точкой входа), State Machine (явные переходы статусов), Factory (сложная сборка), Observer/Pub-Sub, CQRS, Saga.
- **Запрещено:** паттерн «на будущее», «потому что красиво». В колонке «Почему именно он» — конкретная боль из этого эпика.
- В колонке «Альтернатива» — что проще (часто «прямой вызов без паттерна»), почему отвергли.

Эту секцию арх-ревью разбирает построчно — не халтурь.

## Шаг 5: Реализация NFR

Для **каждого** NFR из PRD заполни секцию «Реализация NFR»: техника + где автопроверка. Нет понятной техники — вернись к PRD и **переформулируй** NFR вместе с владельцем продукта. Не оставляй NFR без техники.

## Шаг 6: Сохранение

Обнови строку `🔧 tech-spec.md` в блоке «📚 Артефакты эпика» в `PRD.md` на `✅ готов`.

## Шаг 7: Хендофф

Применяй `../_shared/handoff-protocol.md`:
> Готово: tech-spec эпика `<slug>` — `DOCS_ROOT/<slug>/tech-spec.md`
> Следующий шаг: epic-arch-review
> Промпт: `Запусти epic-arch-review для эпика "<slug>". PRD, preview, tech-spec — в DOCS_ROOT/<slug>/.`

## Принципы

- Конкретика: не «таблица для X», а полная схема с типами.
- Не делай работу arch-review (вердикт) и agile-coach (декомпозиция).
- PRD-AC не покрывается tech-spec'ом — вернись и допиши.
- Технические требования юр-режима (хранение/локализация ПДн, логирование), если режим задан в модуле B project-config, — учитывай в схеме и потоках данных. Полное юр-ревью — отдельный скилл `epic-legal-review`.
