## Ядро AJTBD (вшито в скилл)

Аналитика без AJTBD-каркаса = таблица с конверсиями. Аналитика с AJTBD-каркасом = карта разрывов в графе работ клиента, на каждый разрыв — гипотеза следующего эпика.

### Формат гипотезы инсайта (обязательный)

Каждая гипотеза формулируется в AJTBD-терминах:

> **Сегмент X в триггере Y не доходит до Core Job Z, потому что [категория разрыва].**

Категории разрыва (5 штук — это и есть классификатор всех гипотез):
- **(а) активирующее знание не достигло** — клиент не узнал, что наше Core эффективнее выполняет Big Job, не увидел метрику эффективности, не получил снятия страхов, не понял почему альтернатива хуже;
- **(б) критерий успеха не выполнен** — клиент дошёл до Core Job, но получил результат, не попадающий в его критерии (быстрее ожидаемого / медленнее / не туда / без нужного факта);
- **(в) страх переключения не снят** — клиент видит ценность, но не переключается: страх потери данных, страх «не получится», страх неподдержки, страх социального обесценивания;
- **(г) разрыв критической цепочки (Голдратт)** — клиент прошёл 90% пути, но порвалась цепочка на конкретном шаге (часто последнем — «доставка / онбординг / сдача результата»). 95% работы обнуляются последним звеном;
- **(д) переход на следующую работу не подсказан** — клиент завершил Core Job, но не переходит к следующей работе в цепочке (LTV-разрыв): нет триггера, нет активирующего знания под следующую работу.

«У нас плохая конверсия на шаге 3» — это **не гипотеза**, а наблюдение. Гипотеза = (сегмент × триггер × Core Job × место разрыва в цепочке) → категория разрыва (а-д).

### Критерии успеха AJTBD = метрики продукта

То, что замеряет клиент в голове (критерий успеха его Job) = то, что мы замеряем в аналитике. Источник критериев — PRD эпика (секция «Критерии успеха клиента», заполненная `epic-prd`). Если критерий из PRD не превратился в событие — это либо ошибка `epic-prd`, либо разрыв в `analytics.md`, отдельный класс инсайта.

### Критические цепочки работ (Голдратт)

Воронка = критическая цепочка работ клиента. **Главная утечка воронки = там, где порвалась цепочка**. 7 типов разрывов из AJTBD (для каждого шага воронки проверяй):
- последний шаг (где чаще всего ломается);
- скрытые роли (в B2B — кто в цепочке без ответственного);
- циклы (передача туда-сюда между ролями / экранами);
- задержки с большим разбросом;
- высокая вариативность качества;
- работы без ответственного (никто не подсказывает следующий шаг);
- налоговые работы (клиент вынужден доделывать сам).

### Тип работы влияет на интерпретацию метрик

- **Частотные работы** (повторное использование, LTV-продукты): смотри **возврат на N-ю неделю** и **гедонистическую адаптацию** (со временем эффект уменьшается — вчера-вау, сегодня-норма). Сравнивай когорты 1-я vs 4-я vs 12-я неделя. Падение возврата = адаптация, нужны новые ценности.
- **Последовательные работы** (ценность в конце цепочки — ипотека, аренда, обучение): смотри **прохождение этапа** и **скорость до пользы**. Retention решается сокращением шагов до момента, когда клиент получил Big Job, а не количеством фич.
- **Виральные работы** (один клиент тащит другого — Figma, Miro): смотри **K-фактор и качество рекомендации** (conversion рекомендованного пользователя). Количество приглашений без качества — пустая метрика.
- **Налоговые работы** (клиент вынужден доделывать сам): смотри **отвал после касания с налогом**. Налоговые работы — главный убийца повторных покупок.

# Analytics Insights

Замыкаешь цикл: **данные аналитики → AJTBD-гипотезы → вход в `epic-prd`**. Standalone-скилл, запускается по запросу — обычно через 1–2 недели после релиза эпика.

Контекст — `../_shared/project-config.md` + проектный `CLAUDE.md`. Approve — `../_shared/approve-protocol.md`. Источник данных — `ANALYTICS_PROVIDER` + `ANALYTICS_ACCESS` (модуль A project-config). Список событий по фичам — `DOCS_ROOT/<feature-slug>/analytics.md`. Карточки работ — из PRD-эпиков (`DOCS_ROOT/<epic-slug>/PRD.md`, секция AJTBD).

## Старт

Approve **не нужен** для read-only анализа. Модуль A project-config не заполнен (`ANALYTICS_PROVIDER` = «нет») — стоп, скажи пользователю, что аналитики нет и инсайты строить не из чего.

## Шаг 1: Доступ к аналитике

Работаем через `ANALYTICS_ACCESS` (API-токен в ENV / MCP / экспорт). Credentials нет — стоп, попроси у пользователя. Не угадывай числа.

## Шаг 2: Сбор данных

По каждой релизнутой фиче:

1. **События / goals** — из `DOCS_ROOT/<feature-slug>/analytics.md`: воронка, сравнение с прошлым периодом, сегментация по устройствам (mobile-first критично).
2. **Session replay / Webvisor** — топ-5–10 сессий: где зависают, где уходят, что повторяют.
3. **Heatmaps** — клики, скроллы: ложные клики, до какого момента доходят.
4. **Маппинг событий на граф работ.** Прочитай PRD эпика (секция AJTBD — Big Job, Core Job, критерии успеха, тип работы). Каждое событие из `analytics.md` относи к шагу одной из работ:
   - **триггер сработал** = вход в воронку,
   - **клиент в процессе Core Job** = промежуточные шаги,
   - **критерий успеха выполнен** = success-событие,
   - **разрыв критической цепочки** = error / drop-off,
   - **переход на следующую работу** = retention / next-action события.

   Визуализируй разрыв там, где между шагами теряем больше всего. Этот разрыв = главный кандидат на инсайт.

(Если провайдер не даёт какой-то из источников — пропусти явно.)

## Шаг 3: Анализ

Не описывай данные — **выводи AJTBD-гипотезы**. Прочитай `templates/insights.md`. Минимум 3, максимум 10.

Каждая гипотеза = (сегмент × триггер × Core Job × место разрыва в цепочке) → одна из 5 категорий разрыва:

- **(а) Активирующее знание не достигло** — пользователь не увидел / не понял, что Core эффективнее Big Job. Симптомы: высокий отвал на лендинге, низкое время на странице с ключевым сообщением, не доскролливают до соц.доказательства / метрики эффективности. Гипотеза: «Сегмент <X> в триггере <Y> не доходит до <Core Job Z>, потому что активирующее знание (часть <а/б/в>) не загрузилось — клиент не увидел <метрика эффективности / снятие страха / увольнение альтернативы>».

- **(б) Критерий успеха не выполнен** — дошёл до Core, но критерий клиента не попадает (медленнее ожидаемого, не туда, не тот формат результата). Симптомы: success-событие сработало, но за ним идёт повторное действие / уход / негативная сессия в replay. Гипотеза: «Сегмент <X> завершает <Core Job Z>, но критерий успеха <K с метрикой> не выполнен — фактическое значение <число>, ожидаемое <число>».

- **(в) Страх не снят** — видит ценность, но не переключается. Симптомы: высокая глубина просмотра + низкая конверсия в CTA, ложные клики на FAQ / гарантии / отзывы, замирание перед оплатой в replay. Гипотеза: «Сегмент <X> готов к Core Job <Z>, но не переключается из-за страха <конкретный страх>, не снятого <UX-элементом / копи-формулировкой>».

- **(г) Разрыв критической цепочки** — порвалась цепь к Big Job, чаще всего на последнем шаге. Симптомы: воронка проседает резко на одном конкретном шаге; в replay — циклы между экранами; в heatmap — клики мимо ожидаемой зоны. Прогнать 7 типов разрывов (последний шаг / скрытые роли / циклы / задержки / вариативность / без ответственного / налоговые). Гипотеза: «Сегмент <X> теряется на шаге <S> из-за <тип разрыва из 7>».

- **(д) Переход на следующую работу не подсказан** — Core Job завершена, но клиент не переходит к следующей работе в цепочке. Симптомы: success-событие есть, но retention в N-ю неделю проседает; нет триггерных событий следующей работы. Гипотеза: «Сегмент <X> выполнил <Core Job Z>, но не перешёл к <следующая работа W>, потому что в этой точке не загружено активирующее знание под <W>».

**При интерпретации учитывай тип работы** (см. блок «Ядро AJTBD»):
- частотные → когорты по неделям, гедонистическая адаптация;
- последовательные → скорость до пользы, прохождение этапов;
- виральные → K-фактор + качество рекомендации;
- налоговые → отвал после касания с налогом.

## Шаг 4: Файл insights

Создай `DOCS_ROOT/insights/<YYYY-MM-DD>.md` по структуре `templates/insights.md`. Для каждой гипотезы — AJTBD-формат (сегмент × триггер × Job × категория разрыва) + числовое основание + предлагаемый эпик на проверку.

## Шаг 5: Завершение

Заканчивай обычным результатом (standalone-скилл, не хендофф-блок):
> «Инсайты: `DOCS_ROOT/insights/<YYYY-MM-DD>.md`. Топ-гипотеза для следующего эпика: <AJTBD-формулировка: сегмент × триггер × Job × категория разрыва>. Запускать `epic-prd` по ней? — открой новый чат, если да.»

Здесь `?` оправдан — это новый эпик, реальное продуктовое решение пользователя.

## Принципы

- **Гипотеза в AJTBD-формате: сегмент × триггер × Job × место разрыва.** Без этого — это «у нас плохая конверсия», а не гипотеза. Любая гипотеза должна попадать в одну из 5 категорий разрыва (а-д).
- **Не описывай данные — формулируй гипотезы.** Описание = «упало с 60% до 40%». Гипотеза = «Сегмент Z в триггере Y не доходит до Core Job W из-за разрыва критической цепочки на шаге S».
- **Не давай рекомендаций без числа в основании.** Каждая гипотеза = число (конверсия / время / % сегмента) + AJTBD-объяснение.
- **Данных мало (визитов <100, событий <30) — честно: «выводы делать рано».**
- **Session replay — описывай паттерны** в нескольких сессиях, не пересказывай дословно. Паттерны через граф работ: «3 из 5 сессий показывают цикл между шагами X и Y — признак разрыва критической цепочки (Голдратт)».
- **Не путай корреляцию и причинность** — «возможно потому что», а не «потому что». Особенно осторожно с активирующим знанием — его влияние не всегда видно в метриках напрямую.
- **Частотные продукты: смотри гедонистическую адаптацию** (со временем эффект уменьшается). Сравнивай возврат на 1-ю vs 4-ю vs 12-ю неделю. Падение — структурное, не баг.
- **Последовательные продукты: смотри скорость до пользы**, а не количество фич. Retention решается сокращением цепочки до Big Job.
- **Виральные работы: качество рекомендации > количество.** Замеряй conversion рекомендованного пользователя, а не число приглашений.
- **Налоговые работы (клиент доделывает сам) = главный убийца retention.** Ищи их в replay — где клиент делает не то, что ожидал? «Придётся самому» = риск отвала.
- **Главная утечка воронки = последний шаг.** 95% работы обнуляются последним звеном (Голдратт). Если не нашёл утечку на последнем шаге — проверь ещё раз, обычно она там.
- **Сегмент в гипотезе — через работу и критерии**, не через демографию. «Платящие, выполняющие Job X с критерием K» — сегмент. «Мужчины 25-34» — не сегмент.
- **Хочешь завести гипотезы как задачи в трекере** — это отдельный скилл `tracker-sync` по запросу. Файл insights самодостаточен.
