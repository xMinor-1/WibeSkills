# Handoff-протокол — переход между шагами pipeline

**Переход делает сам агент, пользователь ничего не копирует.** Главный чат — дирижёр: доводит текущий шаг
до артефакта на диске и сразу запускает следующий — сабагентом (автономный шаг) или здесь же (диалоговый
и оркестрирующий шаг). Блок «открой новый чат» остался только как ручной режим по запросу.

## Почему так

Контекст растёт с каждым шагом: если гнать эпик целиком в одном контексте, модель «забывает» начало, ответы
дорожают. Сабагент стартует с чистым контекстом, читает артефакты из `DOCS_ROOT/<epic-slug>/` и возвращает
в главный чат короткий отчёт. Контекст дирижёра растёт на отчёты, а не на работу шагов.

## Где исполняется шаг

| Где | Шаги | Почему |
|---|---|---|
| Главный чат | `kickoff`, `market-research`, `craft-value-proposition`, `epic-prd`, `mvp` | диалог с пользователем по ходу работы |
| Главный чат | `delivery-run`, `task-cross-review` (ручной путь), `task-ship` | сами запускают сабагентов или Workflow; деплой с approve |
| Сабагент | `ux-patterns`, `epic-preview` (генерация), `epic-tech-spec`, `epic-arch-review`, `agile-coach decompose`, `dev-handoff`, `task-build` / `task-test` / `task-docs` (ручной путь) | автономная работа до артефакта или до гейта |

Гейты ⏸ и approve — всегда в главном чате, даже если шаг шёл в сабагенте.

## Как дирижёр запускает сабагента

1. Одна строка пользователю: `→ <скилл> (сабагент): <что делает>`.
2. Agent tool: `subagent_type: general-purpose` (или тип, который требует SKILL.md шага), `description: <скилл> <slug>`,
   промпт по контракту ниже. По умолчанию в фоне: пользователь может писать, пока шаг идёт;
   работу сабагента не дублируй и результат не предсказывай.
3. Пришёл отчёт — обработай по статусу (таблица ниже).

**Контракт промпта:**
- Первая строка — самодостаточная задача шага: скилл + slug эпика/Story + пути к артефактам. Это строка
  «Промпт» из секции «Хендофф» предыдущего скилла.
- «Прочитай `<библиотека>/<скилл>/SKILL.md` и упомянутые в нём `_shared/*.md` с диска и работай по ним
  в режиме сабагента (`_shared/handoff-protocol.md`, раздел «Режим сабагента»)». Абсолютный путь к библиотеке —
  из «Base directory» загруженного скилла: сабагент библиотеку скиллов не видит.
- Корень проекта, `DOCS_ROOT`, решения владельца из главного чата, которых ещё нет в артефактах, — дайджестом,
  не пересказом переписки.
- Форма отчёта:

```
Статус: ok | needs_input | needs_approve | gate | needs_decision | blocked
Артефакты: <пути>
Итог: <2–5 строк на бизнес-языке>
Вопросы / план / что проверить: <только при статусе не ok — с вариантами и рекомендацией>
Следующий шаг: <скилл> — <промпт по карте> | нет
```

## Режим сабагента

Сабагент работает по своему SKILL.md, кроме пунктов:
- **С пользователем напрямую не говорит.** Вопрос, без которого дальше нельзя (продуктовый выбор, UX, данные,
  которых нет на диске), — статус `needs_input`: работа останавливается в точке вопроса, черновик — на диск.
  Технические решения принимает сам.
- **Approve-операции не выполняет** ([approve-protocol.md](approve-protocol.md)) — `needs_approve` + план на языке владельца.
- **Гейт ⏸ не проходит** — `gate` + что проверить и где.
- **Следующий шаг не запускает** и хендофф-блок не печатает — пишет следующий шаг в отчёт.
- **Вложенного сабагента запустить не может:** если SKILL.md велит позвать сабагента (`code-explorer`, `code-architect`),
  делает эту часть сам.
- Отчёт короткий: содержательное — в артефактах на диске.

## Как дирижёр обрабатывает отчёт

| Статус | Что делает дирижёр |
|---|---|
| `ok` | 1–3 строки пользователю (что готово, где лежит) → сразу следующий шаг по карте, без вопроса «продолжать?» |
| `needs_input` | задаёт вопросы пользователю (с вариантами — через AskUserQuestion) → ответ тому же сабагенту через SendMessage, контекст сабагента сохранён; сабагент недоступен — новый, с ответом в промпте |
| `needs_approve` | план на бизнес-языке → ждёт ✅ → SendMessage «approve получен, выполняй» |
| `gate` | говорит, что проверить → ждёт ✅ / ❌ → ✅: следующий шаг; ❌: замечания тому же сабагенту на доработку |
| `needs_decision`, `blocked` | причина и варианты на бизнес-языке, ждёт решения |

Артефакт целиком дирижёр не читает ради пересказа — только отчёт. Читает, когда это нужно для вопроса гейта
или пользователь просит.

Механическую доработку после ответа (переименовать черновик, отметить статус артефакта) дирижёр делает сам:
поднимать сабагента ради неё — платить за повторное чтение всего его контекста.

**Дирижёр останавливается сам:** на гейтах и approve; в конце ветки карты (эпик закрыт, вердикт market-research
⚠️ / ❌); на «стоп» / «пауза» от пользователя — доводит текущий шаг до артефакта и называет следующий.

## Ручной режим — хендофф-блок

Когда: пользователь просит промпт для нового чата, переносит работу в другой тред или на другую машину,
главный чат разросся, харнесс без сабагентов. Блок — последнее в сообщении:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🚪 ХЕНДОФФ — открой новый чат

Готово: <что сделано, где лежит артефакт — 1 строка>
Следующий шаг: <название-скилла>

Вставь в новый чат:
┌──────────────────────────────────
│ <самодостаточный промпт: скилл + slug эпика/Story + путь к артефактам>
└──────────────────────────────────
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

Пример промпта: `Запусти epic-tech-spec для эпика "otp-auth". PRD и preview лежат в docs/otp-auth/.`

## Карта pipeline (единая карта маршрутизации)

Это ЕДИНСТВЕННОЕ место, где описано «какие скиллы когда». Оси: TRACK ([tracks.md](tracks.md)) и MODE ([mode.md](mode.md)) — они ссылаются сюда, копий карты нигде нет. Каждая стрелка — переход дирижёра; «Где» — по таблице выше.

**Вход:** новая задача без явного скилла → `kickoff` (роутер: где живёт, MODE+TRACK → `epic-meta.md`). Явные вызовы скиллов и промпты из ручного режима — сразу в скилл, без kickoff.

| Шаг (скилл) | TRACK | Где | Следующий шаг | Гейт перед переходом |
|---|---|---|---|---|
| `mvp` | fast | главный чат | — (бриф → код/прототип → результат, один заход) | ⏸ показ перед боевым деплоем |
| `market-research` *(опц.)* | indie / enterprise | главный чат | `craft-value-proposition` или `epic-prd` | — (вердикт «идея жизнеспособна») |
| `craft-value-proposition` *(опц.)* | indie / enterprise | главный чат | `epic-prd` | — (выбран primary value prop) |
| `epic-prd` | prd | главный чат | `agile-coach decompose` (PRD-machine + lite-tech-spec-секция, без preview/arch-review) | — |
| `epic-prd` | indie / enterprise | главный чат | `ux-patterns` (пропуск — по явному «без исследования» → `epic-preview`) | — |
| `ux-patterns` | indie / enterprise | сабагент | `epic-preview` | — (паттерн-контракт в `ux-patterns.md`; режим light — минуты, если база паттернов уже накоплена) |
| `epic-preview` | indie / enterprise | сабагент | `epic-tech-spec` | ⏸ визуальный осмотр preview в браузере |
| `epic-tech-spec` | indie / enterprise | сабагент | `epic-arch-review` (app) / `dev-handoff` (work) | — |
| `epic-arch-review` (app-only) | indie / enterprise | сабагент | `agile-coach decompose` | NO-GO → возврат в `epic-tech-spec` / `epic-prd` |
| `agile-coach decompose` | prd / indie / enterprise | сабагент | `delivery-run` (app) / `dev-handoff` (work) | approve на запись Stories/Tasks в `stories.md` |
| `delivery-run` (app-only) | prd / indie / enterprise | главный чат | сегментами до гейтов; Story готова → `task-ship` | ⏸ Story manual gate на prod-build |
| `task-ship` | prd / indie / enterprise | главный чат | следующий сегмент `delivery-run`; эпик закрыт → — | ⏸ бизнес-summary + ✅ перед деплоем; через 1–2 недели `analytics-insights` |

**Ручной путь delivery** (вместо `delivery-run`): `task-build` → `task-cross-review` (CHANGES → назад, лимит 2 раунда) → `task-test` → `task-docs` → следующая Task; последняя Task Story → ⏸ manual gate → `task-ship`. Шаги — сабагентами, `task-cross-review` — в главном чате (сам запускает линзы).

**Вне pipeline (standalone, по запросу):** `nmt-chat`, `triz-resolve`, `video-distill`, `watch` (просмотр видео по ссылке: транскрипт + кадры по сменам сцен), `helpx5`, `epic-legal-review`, `tracker-sync`, `todo` (быстрый захват задач в GitHub Issues — не путать с `agile-coach`/`tracker-sync`), `analytics-insights`, `pipeline-retro`, все `marketing-*`, `go`/`goon` (утилиты фоновых сессий), `response-optimizer` (хук-скилл, вызовов не имеет). Они следующий шаг не запускают — заканчивают обычным коротким результатом.

## Реальные гейты ⏸

Гейт = действие живого человека. Шаг доводит до гейта и говорит, что проверить; дирижёр **ждёт ответ пользователя** и только потом делает переход.

- `epic-preview` — пользователь открывает preview в браузере, говорит ✅ / переделай.
- `task-test` (последняя Task Story) — Story manual gate: пользователь открывает на prod-build, проверяет AC Story.
- `task-ship` — бизнес-summary что меняется + ✅ перед деплоем.

## Возвратные петли

Возврат назад — переход, направленный назад: тому же сабагенту через SendMessage, если он жив, иначе новый сабагент с промптом-возвратом.

| Петля | Лимит | После лимита |
|---|---|---|
| `cross-review` → `build` | 2 раунда per Task | эскалация пользователю: «не сходимся, нужно решение» |
| `task-build` `LOCAL_CHECK` авто-fix | 3 попытки | стоп, отчёт |
| `task-test` unit авто-fix | 3 попытки | стоп, отчёт |
| `task-test` e2e авто-fix | 1 повтор | стоп, отчёт |
| `arch-review` NO-GO → `tech-spec`/`prd` | — | возврат с конкретным списком |

Счётчик раунда пиши в `stories.md` рядом с Task (`cross-review раунд 2/2`) — виден в стендапе.

## Запреты

- Не печатай хендофф-блок, если пользователь не просил ручной режим.
- Не спрашивай «запустить следующий шаг?» — запускай; исключения — гейты и approve.
- Не тащи в промпт сабагента переписку — артефакты на диске и дайджест решений.
- Не проходи ⏸-гейт сам и не выполняй approve-операции без ответа человека.
- Не запускай второй сабагент на тот же шаг, пока первый работает.

## Откат

Авто-переход что-то ломает — пользователь говорит «по-старому» или «стоп», шаг идёт в ручном режиме. Корректировка карты — на ближайшем `pipeline-retro`.
