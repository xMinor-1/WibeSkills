# Delivery-workflow — контракт авто-оркестрации

Как скилл `delivery-run` исполняет цепочку `task-build → task-cross-review → task-test → task-docs`
через инструмент **Workflow** (сабагенты с чистым контекстом). Заменяет ручные хендоффы
«открой новый чат» на delivery-участке; discovery остаётся ручным ([handoff-protocol.md](handoff-protocol.md)).

## Модель: 1 ран = 1 безгейтовый сегмент

Workflow не умеет ждать человека посреди рана. Поэтому:

- **Сегмент** = Tasks одной Story (или нескольких параллельных Stories) до ближайшего
  человеческого гейта (Story manual-gate, ship).
- Скрипт генерируется так, чтобы **завершиться на границе гейта**. После ✅ пользователя
  delivery-run генерирует скрипт следующего сегмента из актуального stories.md.
- Упавший ран возобновляется через `resumeFromRunId` (готовые стадии — из кэша).
- `log()` внутри рана — технический прогресс. **Сводку по Story на бизнес-языке и вопрос
  гейта задаёт главный агент после завершения рана** ([communication-style.md](communication-style.md)).

## Кто что делает (роли)

| Роль | Кто | Что делает |
|---|---|---|
| Оркестратор | главный агент (скилл delivery-run) | читает stories.md, генерирует скрипт (граф — константой: у скрипта нет FS-доступа), запускает ран, сливает git, пишет статусы, держит гейты |
| build-сабагент | `EXECUTOR`, свой worktree | код одной Task по SKILL.md task-build (Workflow-режим), коммит в task-ветке, возвращает branch+sha |
| review-сабагенты | `REVIEWER` (строго выше исполнителя), 2 параллельных, read-only | линзы task-cross-review по diff Story-ветки; **их запускает оркестратор** — сабагент не может спавнить вложенных |
| test-сабагент | sonnet, Story-worktree | task-test (Workflow-режим), последовательно после слива |
| docs-сабагент | sonnet | task-docs (Workflow-режим) |

## Git-контракт (single-writer)

1. build-сабагент работает в **изолированном worktree** с веткой `task/<epic>/<task-slug>`
   (создаёт оркестратор или сам агент по промпту), коммитит, возвращает `branch`+`sha`.
2. **Оркестратор** сливает task-ветку в Story-ветку `feature/<epic>/<story>` (merge --no-ff)
   **до** запуска review/test. Ревьюеры читают diff Story-ветки, test гоняет её код.
3. Task-и одной Story — строго последовательны; параллелизм — только между Story
   без пересечения `touches` (граф в stories.md).
4. **Статусы stories.md пишет только оркестратор** между стадиями по structured output
   сабагентов. Сабагентам запись в stories.md запрещена (см. [backlog.md](backlog.md)).
5. Параллельные группы бьются на пачки: не более **3** одновременных build-сабагентов
   (RAM хоста; здесь же живут прод-сервисы).

## Стадия dispatch (когда код пишет не оркестратор)

Включается, если `EXECUTOR` в project-config ≠ `inherit`. Протокол —
[executor-protocol.md](executor-protocol.md). Стадия `build` разворачивается в четыре шага:

| Шаг | Кто | Что |
|---|---|---|
| **package** | топ-модель, `task-build` режим contract | дописывает пакет Task: контракт интерфейсов + красные тесты (прогнаны, падают), коммит в task-ветку |
| **dispatch** | исполнитель из `EXECUTOR` | получает **только** путь к пакету и worktree; делает тесты зелёными |
| **verify** | скрипт `VERIFY_CMD` | точечные тесты + typecheck + diff в границах «Разрешено править»; exit-code = вердикт |
| **review** | 2 линзы `task-cross-review` на модели `REVIEWER` | безопасность/юр-режим + соответствие AC; BLOCK на выход за границы пакета |

**Частота стадий.** `package` → `dispatch` → `verify` идут на **каждую Task**. Стадия `review`
собирается **на Story целиком** — линзы читают связный diff Story-ветки один раз, а не по разу
на каждую из её Task. Исключение: Task с approve-поверхностью (миграции, auth/payments) ревьюится
сразу. Лестница `EXECUTOR_EFFORT` (ретрай поднимает ступень) — в
[executor-protocol.md](executor-protocol.md).

Значения `EXECUTOR` и как их исполняет оркестратор:

- `sonnet` / `haiku` — обычный сабагент Workflow с `model: <значение>`, промпт = «прочитай пакет
  `<путь>`, работай по нему, PRD и tech-spec не читай».
- `external:<команда>` — **не** сабагент: оркестратор запускает команду через Bash в worktree Task,
  передаёт путь к пакету аргументом, читает stdout. Внешнюю модель нельзя позвать сабагентом
  внутри рана — инструмент Workflow принимает только модели Anthropic.

`verify` красный → возврат исполнителю, лимит 3 попытки (лимит считает оркестратор, не исполнитель).
Исчерпан → `needs_decision`. Красный `verify` из-за выхода за границы возврату не подлежит:
сразу `needs_decision` — исполнитель уже показал, что не держит рамку.

После каждой Task оркестратор дописывает строку в `DOCS_ROOT/<epic-slug>/delivery-log.jsonl`
(поля — в executor-protocol.md, раздел «Метрики»). Это единственный источник для сравнения
исполнителей между собой.

## Контракт промпта сабагента

Промпт каждого сабагента включает:
- **Цель**: Task-slug, AC задачи, `touches`, `deps`, пути к PRD/tech-spec (или PRD-machine
  с lite-tech-spec-секцией для TRACK=prd) — дайджест, не пересказ переписки.
- **Указание прочитать** свой SKILL.md с диска (сабагенты не видят библиотеку скиллов)
  и работать по его секции **«Workflow-режим»**.
- **Shape structured output**: status + данные стадии (build: branch/sha; review: вердикт
  и находки; test: результат прогонов; docs: пути файлов).

## Skip-список Workflow-режима (что сабагент НЕ делает)

- НЕ создаёт Story-worktree (шаг worktree-protocol) — изоляцию даёт оркестратор.
- НЕ готовит хендофф-блоки «открой новый чат».
- НЕ ждёт ответа человека на гейтах — возвращает результат, гейт держит оркестратор.
- НЕ пишет статусы в stories.md.
- НЕ выполняет approve-операции ([approve-protocol.md](approve-protocol.md)): миграции БД,
  auth/payments, деструктивный git → возвращает `needs_approve`, решает человек между сегментами.

## Стоп-статусы (динамические гейты)

Сабагент возвращает в structured output один из:
- `ok` — стадия пройдена;
- `needs_decision` — исчерпан лимит петли (лимиты из handoff-protocol §«Возвратные петли»:
  cross-review 2 раунда, авто-fix 3/3/1) — оркестратор завершает сегмент, главный агент
  докладывает и ждёт решения;
- `needs_approve` — операция approve-класса;
- `blocked` — внешняя блокировка (нет доступа, сломан пререквизит).

Любой не-`ok` завершает ран на этой границе как динамический гейт.

## Ручной фоллбэк

Хендофф-модель «один скилл = один чат» полностью работоспособна: любой шаг можно пройти
руками через task-* скиллы как раньше. delivery-run — ускоритель, не замена.
