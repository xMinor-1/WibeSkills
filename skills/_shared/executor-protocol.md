# Executor-протокол — передача написания кода любому исполнителю

Как оформить Task так, чтобы её мог выполнить **не тот, кто её проектировал**: младшая модель
(Sonnet/Haiku), модель другого провайдера (DeepSeek, Qwen) или живой джун. Проектирование
и приёмка остаются у топ-модели.

Дополняет [delivery-workflow.md](delivery-workflow.md) (оркестрация внутри Claude) и
[backlog.md](backlog.md) (формат Task). Не заменяет их: без пакета pipeline работает как раньше.

## Зачем

Task в `stories.md` — одна строка (slug, `touches`, `deps`), AC живут на уровне Story,
детали — в tech-spec на сотни КБ. Исполнителю с контекстом 128k этого не собрать, а исполнителю
без доступа к переписке — тем более. **Task-packet** — самодостаточный файл на одну Task:
всё нужное внутри, ничего лишнего.

## Три роли

| Роль | Кто делает | Что производит | Можно ли отдать вниз |
|---|---|---|---|
| **architect** | топ-модель | декомпозиция, контракт интерфейсов, красные тесты, сам пакет, синтез ревью, разрешение конфликтов | нет — здесь цена ошибки максимальна |
| **implementer** | любая приличная кодинг-модель | тела функций по готовому контракту, пока красные тесты не позеленеют | **да — это и есть цель протокола** |
| **verifier** | скрипт + средняя модель | детерминированная проверка (`VERIFY_CMD`) + 4 линзы cross-review | частично: скрипт-часть не зависит от модели |

Разделение проходит по границе «решение принято» / «решение исполнено». Всё, где нужно
выбрать между вариантами, — у architect. Всё, где вариант уже выбран и записан, — у implementer.

## Task-packet

Файл `DOCS_ROOT/<epic-slug>/tasks/<task-slug>.md`, шаблон — [templates/task-packet.md](templates/task-packet.md).
Строка Task в `stories.md` остаётся индексом и получает ссылку на пакет — формат бэклога не меняется.

**Контракт входа** — пакет обязан содержать всё из списка, иначе исполнитель начнёт додумывать:

| Секция | Обязательна | Что ломается без неё |
|---|---|---|
| Цель (1 строка) | да | исполнитель решает свою задачу, не вашу |
| AC этой Task (2–5, проверяемых) | да | нечем определить готовность |
| Контракт интерфейсов (готовые сигнатуры/типы/порты) | да, если Task не изолирована | зависимые Task ломаются об чужие имена |
| Разрешено править (точный список путей) | да | правки расползаются по репозиторию |
| Красные тесты (пути + команда) | да для логики; для чистого UI — visual baseline | тест подгоняется под реализацию |
| Команда проверки (`VERIFY_CMD`) | да | «у меня работает» вместо вердикта |
| Выдержки из спеки (абзацы, не ссылки) | да | исполнитель тянет 400 КБ или не тянет ничего |
| Вырезка экрана preview (для UI-Task) | да | эталон целиком не влезает в контекст: на живом проекте это сотни КБ |
| Запреты | да | «попутно поправил» |
| Формат ответа | да | результат нечем разобрать автоматически |

**Правило самодостаточности:** пакет проходит проверку, если исполнитель, у которого есть
только пакет + репозиторий кода (без PRD, tech-spec и переписки), может выполнить Task
без единого вопроса. Не проходит — дополняй пакет, а не инструктируй исполнителя.

**Правило объёма:** 150–250 строк. Больше — значит Task слишком крупная, режь надвое.
Меньше — вероятно, недосказано; проверь по таблице выше.

**Машиночитаемые якоря.** Две секции пакета читает скрипт, поэтому теги fence-блоков строгие:
` ```allowed-paths ` — список разрешённых путей (от корня git-репо, glob допустим),
` ```test-cmd ` — команда точечного прогона тестов Task. Остальной пакет — свободный markdown
для исполнителя-человека или модели.

## Контракт выхода

Исполнитель завершает работу JSON-объектом (последний блок ответа, ничего после него):

```json
{
  "status": "ok",
  "task": "<task-slug>",
  "branch": "task/<epic>/<task-slug>",
  "sha": "<commit sha>",
  "files": ["src/...", "src/..."],
  "not_done": [],
  "summary": "1–2 строки: что сделано"
}
```

| status | Когда | Что делает оркестратор |
|---|---|---|
| `ok` | все красные тесты зелёные, `VERIFY_CMD` прошёл | merge в Story-ветку → cross-review |
| `needs_approve` | упёрся в операцию approve-класса ([approve-protocol.md](approve-protocol.md)) | останавливает сегмент, спрашивает человека |
| `blocked` | внешняя блокировка: нет доступа, сломан пререквизит | останавливает, докладывает |
| `needs_decision` | исчерпан лимит попыток, решение за человеком | останавливает, эскалирует |

Исполнитель **не пишет** статусы в `stories.md` и не мержит ветки — состояние ведёт оркестратор
(single-writer, [delivery-workflow.md](delivery-workflow.md)).

## Границы sandbox

`Разрешено править` из пакета = единственная зона записи. Всё остальное read-only.

Проверка обязательна и делается **скриптом, а не доверием**: `VERIFY_CMD` сравнивает
`git diff --name-only` со списком разрешённых путей. Выход за границы — вердикт BLOCK
в cross-review, независимо от качества самого кода.

Почему жёстко: расползание правок — типовой отказ слабой модели, и оно же ломает
параллельность Task (граф `touches` в `stories.md` перестаёт быть правдой).

## Запреты исполнителю

Пишутся в каждый пакет дословно:

1. Не править тест, чтобы он позеленел. Тест неверен — вернуть `needs_decision` с обоснованием.
2. Не менять сигнатуры, типы и имена из «Контракта интерфейсов».
3. Не трогать миграции и схему БД (approve-класс).
4. Не «улучшать» preview-эталон — расхождение с ним есть дефект реализации.
5. Не править файлы вне списка разрешённых, даже очевидные опечатки.
6. Не отключать проверки: без `--no-verify`, без `skip`/`only` в тестах, без `@ts-ignore`.
7. Не добавлять зависимости — новый пакет требует решения architect.

## Подключение внешнего исполнителя

**Вариант A — прокси под видом Anthropic API.** `ANTHROPIC_BASE_URL` на LiteLLM или
claude-code-router, за ним модель другого провайдера. Весь pipeline работает как есть,
меняется «мозг» целиком.

- плюс: нулевые правки в скиллах;
- минус: чужая модель занимает **все** роли сразу, включая оркестрацию и синтез ревью — там,
  где слабая модель опаснее всего;
- статус: механизм такого проксирования существует, но **точную совместимость с текущей версией
  харнесса надо проверять экспериментом**, а не принимать на веру. До проверки — считать гипотезой.

**Вариант B — внешний CLI как инструмент на стадии fill (рекомендуется).** Оркестратор и приёмка
остаются на топ-модели, наружу уходит только реализация:

```
architect (топ) → пакет + красные тесты
      ↓
implementer (EXECUTOR из project-config) → код
      ↓
verifier: VERIFY_CMD (скрипт) → cross-review (4 линзы, топ/средняя модель)
```

Поле `EXECUTOR` в project-config задаёт исполнителя: `inherit` (та же модель, что и оркестратор),
`sonnet`/`haiku` (младшая модель Anthropic), `external:<команда>` (внешний CLI, получает путь
к пакету аргументом и работает в выданном worktree).

- плюс: провайдера можно менять на уровне отдельной Task; приёмка не зависит от исполнителя;
  падение внешнего CLI не роняет прогон;
- минус: нужна стадия dispatch в оркестраторе (описана в delivery-workflow.md).

Рекомендация: **B для работы, A — разово, для калибровочного замера**.

## Когда пакет не нужен

Не превращай протокол в бюрократию. Пакет оправдан, когда исполнитель ≠ проектировщик:

| Ситуация | Пакет |
|---|---|
| `EXECUTOR: inherit`, TRACK=fast/mvp, одноразовый прототип | не нужен — работай как раньше |
| Task тривиальная (правка копирайта, конфиг) | не нужен |
| `EXECUTOR` = младшая модель или внешний CLI | обязателен |
| Task в графе имеет зависимые (`deps` ссылаются на неё) | обязателен — контракт интерфейсов защищает соседей |
| Возврат после cross-review с фиксами | достаточно дополнить пакет секцией «Фиксы раунда N» |

## Метрики (для сравнения исполнителей)

Оркестратор пишет по каждой Task в `DOCS_ROOT/<epic-slug>/delivery-log.jsonl`:

```json
{"task":"S4-2","executor":"sonnet","first_pass_green":true,"review_rounds":1,
 "autofix_attempts":0,"out_of_scope_files":0,"wall_clock_s":412,"cost_usd":0.83}
```

Четыре числа, по которым исполнители сравнимы между собой: **доля зелёных с первого прогона ·
число раундов cross-review · выходы за `touches` · стоимость**. Разбор — в `pipeline-retro`.
Без лога сравнение моделей превращается в ощущение.
